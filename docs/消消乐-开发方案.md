## 一、方案概述

### 1.1 要做什么

在 `client-v2/` 中新增一个三消游戏「消消乐」，包含两种主模式 + 一个娱乐层：

- **闯关模式**：步数制，按关卡目标与星级推进
- **无尽模式**：无时间无步数限制，玩家自由结算，按分数排名
- **娱乐模式**：二级菜单，放不设关卡与目标的玩法，当前有「无尽三色」（5.5）与「肉鸽试炼」（5.6），成绩各自独立

### 1.2 为什么只做 v2

- 消消乐是**纯单人玩法**，不涉及匹配、房间、悔棋、观战、回放等联机协议
- v2 是原生 ES Modules + 无构建，新增一个游戏模块的边际成本远低于改动 `client/index.html`（12672 行单文件）
- 与既有策略一致：**v1 冻结只维护，v2 主力开发**；v1 未来会被 v2 全量替代
- 参考对象是现有的贪吃蛇（同为"单人本地逻辑 + 结束后上报"），是现成的最佳模板

### 1.3 不做什么

| 不做 | 原因 |
|---|---|
| v1 客户端实现 | v1 结构不适合大改，且未来会被 v2 替代 |
| 联机对战 / 观战 / 回放 | 玩法性质不需要，且能省掉一整条链路 |
| 个人资料页展示消消乐进度 | 控制改动面，入口为导航项 + 排行榜 + 成就 |
| 特殊元素两两组合（条状+条状=十字等） | 分支数量是 n² 级别，v1 只保留"彩球 + 任意" |
| 关卡编辑器与创意工坊 | 未来展望，等消消乐玩法稳定后再做（见 `关卡平台-设计方案.md`）；首版只满足 UGC-ready 约束（见 4.5） |

## 三、核心玩法设计

### 3.1 核心循环

```
玩家交换相邻方块
      ↓
匹配三连及以上（横/竖同色，含 L/T 形）
      ↓
消除、下落、顶部补充
      ↓
连锁判定 ──还能连锁──→ 回到匹配
      ↓ 无连锁
回合结束（无可行步则重排棋盘）
```

**连锁（Cascade）是这个游戏的核心爽点**，也是无尽模式的主要得分来源。

### 3.2 棋盘自由度与参数

棋盘**不固定尺寸也不固定形状**，形状与参数逐关配置——这是关卡设计的主要表达手段。

**自由度分层**

| 层级 | 形态 | v1 是否支持 |
|---|---|---|
| L0 | 任意矩形（如 7×8、9×10） | ✅ |
| L1 | 异形：在矩形范围内挖洞，形成菱形 / 十字 / 环形等奇怪排列 | ✅ |
| L2 | 分仓多区域：洞把棋盘切成互不相连的几块，各自独立下落 | ✅ |
| L3 | 可变重力方向（向上 / 向左掉落）、传送门、多层棋盘 | ❌ 预留，v1 不做 |

关键实现结论：**L1 与 L2 不需要写两套逻辑**。只要下落按「同一列内的连续可玩段」处理，洞与分仓就自然成立——洞把列切断成多段，每段独立下落即可。

**参数范围**（逐关可配）

| 参数 | 范围 | 默认 |
|---|---|---|
| 行 × 列 | 8 ~ 12 行 × 8 ~ 10 列 | 8 × 8 |
| 可玩格子上限 | ≤ 120 | — |
| 元素种类 | 4 ~ 8 | 6 |
| 重力方向 | v1 固定 `down` | `down` |

元素种类的取舍：少于 4 种太容易连锁，多于 8 种挫败感强。闯关模式第 1 章（完整矩形）用 5 种，第 2 / 3 章（挖洞 / 分仓的碎格子棋盘）压到 4 种——碎格子棋盘没有完整行列可借力，颜色一多就频繁出现「全盘无可行步 → 只能靠系统洗牌」（实测 6 色时有 6 关平均每 60 步要洗 3~7 次牌，降到 4 色后基本归零），目标值已按 4 色重新标定。无尽模式随分数分档从 4 提到 8（见 5.2），并用「颜色数得分倍率」抵消低颜色数的得分红利。

**分仓棋盘的一处特别注意**：如果某个区域完全没有可行交换，不能对整个棋盘洗牌（会破坏其他区域的局面），洗牌逻辑要以「区域」为粒度（见 3.6）。

### 3.3 消除规则

- 横或竖方向同色 3 连及以上触发消除
- 匹配判定分两趟扫描：先扫全部行，再扫全部列，O(n²)
- **洞会自然切断连线**：扫描时跳过不可玩格子，因此异形棋盘不需要任何特判——挖了洞，连线自己就断了
- **形态识别优先级**：先识别 L/T 形（交叉），再识别直线 5 连，再识别直线 4 连，最后才是普通 3 连

### 3.4 交换规则

- 只接受**能形成消除**的交换，非法交换播放回弹动画
- 这是三消手感的关键，必须做，不能省

### 3.5 特殊元素

| 触发形态 | 生成元素 | 效果 |
|---|---|---|
| 4 连（横） | 横条 | 消除整行 |
| 4 连（竖） | 竖条 | 消除整列 |
| 5 连直线 | 彩球 | 消除全场同色 |
| L / T 形（横竖各 ≥3 共用一格） | 炸弹 | 消除 3×3 范围 |

三条必须定死的规则：

1. **生成位置**：特殊元素生成在玩家**交换的那一格**（行业标准做法，手感最好）
2. **级联触发**：特殊元素被波及消除时立即触发其效果，效果再波及到其他特殊元素则继续触发。用 while 队列处理，并设置触发上限以防死循环。**彩球是例外**：条状 / 炸弹的爆炸不波及彩球，扫到也原地保留（不触发、不消耗），彩球只在玩家主动拿它去交换时才结算
3. **组合玩法**：v1 只保留「彩球 + 任意」一条，其余组合不做
   - 彩球 + 普通方块 / 彩球：清除全场同色 / 清空全盘
   - 彩球 + 条状 / 炸弹：把该特殊效果**复制给全部同色棋子**，再逐颗触发（复制保留颜色）

### 3.6 死局处理

- 无任何可行交换时自动洗牌
- **洗牌后必须复检**，避免洗出新的死局
- 洗牌与复检都**只在可玩格子内**进行
- **分仓棋盘以「区域」为粒度**：某个区域死局时只重排该区域，不能让整个棋盘一起洗，否则会破坏其他区域的局面

### 3.7 棋盘数据结构

**棋盘本身要携带形状信息**，不能只是一个二维数组：

```js
// 可玩性判断
grid.isPlayable(r, c)        // mask[r][c] === 1

// 按列拆成若干连续可玩段，供下落逻辑使用
// 洞把一列切成多段，每段独立下落 —— 异形与分仓由此自然支持
grid.columnSegments(c)       // → [{ from, to }, ...]

// 区域（连通块）划分，供分仓洗牌与死局判定使用
grid.regions()               // → [ Set<cellIndex>, ... ]

// 坐标映射（渲染用，异形棋盘不能靠统一 grid 布局）
grid.toPixel(r, c)           // → { x, y }
```

单元格从纯数字升级为对象：

```js
{ color: 1..8, special: null | 'row' | 'col' | 'bomb' | 'rainbow' }
```

## 四、闯关模式设计

### 4.1 规则

| 项 | 规则 |
|---|---|
| 结束条件 | 步数制，每关固定步数，用完即结算 |
| 目标类型 | ① 得分达标 ② 收集指定颜色 N 个 ③ 清除全部障碍（冰块/石头/锁链） |
| 星级 | 3 星 = 通关且剩余步数 ≥ 30%；2 星 = 剩余步数 ≥ 10%；1 星 = 通关（剩余 0 步） |
| 解锁 | 通关后解锁下一关；星级用于展示与奖励 |

### 4.2 关卡数据

配置放客户端 `levels.js`（跟随版本发布，离线可玩，服务端不做配置管理）。单人游戏数值被修改可接受。

```js
{
  id: 1,
  name: '初入糖果镇',

  // 棋盘形状：逐关可变
  rows: 8,
  cols: 8,
  // 可玩格遮罩，1 = 可玩，0 = 洞；留空则整块矩形全可玩
  // 用字符串数组是为了手工设计关卡时可读（不用数数字）
  mask: [
    '11111111',
    '11111111',
    '11001111',
    '11001111',
    '11111111',
    '11111111',
    '11111111',
    '11111111',
  ],

  colors: 5,                  // 本关元素种类（可低于默认 6）
  moves: 20,                  // 步数上限
  goals: [
    { type: 'score', target: 3000 },
    { type: 'collect', color: 'red', target: 15 },
    { type: 'clearBlockers', target: 8 },
  ],
  blockers: [ { r: 3, c: 4, kind: 'ice', hp: 2 } ],
  initial: null,              // 可选：显式指定初始布局；为空则按规则生成
  gravity: 'down',            // 预留字段，v1 固定 'down'
  starScore: 3000,            // 1 星门槛
}
```

**初始化规则**：`initial` 为空时按 `colors` 随机生成，且必须满足两个约束——**棋盘上不存在现成的三连**、**至少存在一个可行交换**。这两条由生成器保证，不依赖关卡配置的正确性。

### 4.3 关卡规模

首版做 **30 关（3 章 × 10 关）**，用于验证难度曲线。

章节按棋盘形态递进，让「形状」本身成为难度与新鲜感的来源：

| 章节 | 关卡数 | 棋盘形态 | 目标 |
|---|---|---|---|
| 第 1 章 | 10 | 标准矩形为主，尺寸逐步变大 | 得分 / 收集 |
| 第 2 章 | 10 | 引入异形（挖洞：菱形、十字、环形） | 增加清除障碍 |
| 第 3 章 | 10 | 引入分仓多区域 + 混合形态 | 三类目标混用 |

**每关棋盘形状不同是设计目标，不是副作用**——这决定了关卡配置不能靠程序批量生成，必须有开发期校验（见风险清单）。

### 4.4 关卡列表 UI

按章节分组的网格，显示星数与锁定态。**不做卷轴大地图**，避免一上来就产生美术资源需求。

### 4.5 UGC-ready 约束

关卡编辑器与创意工坊属于未来展望（见 `关卡平台-设计方案.md`），**不在本方案范围内**。但为了让将来接入平台时不需要重构，首版就要满足以下约束。

这些约束**不增加额外工作量**，只是写法上的要求：

| 约束 | 要求 |
|---|---|
| payload 是纯数据 | 关卡配置只包含 JSON 可序列化的值，不含函数、类实例、DOM 引用 |
| 可从外部加载 | 引擎必须支持「传入一个 payload 直接开局」，不依赖模块内部 state 或游戏流程的既有状态 |
| 可重复加载 | 同一 payload 反复加载得到完全相同的局面，**不能有随机残留**——随机生成必须只在生成阶段发生一次（或使用可播种随机），引擎内部不得调用 `Math.random` |
| 带 `schemaVersion` | 每关携带 `schemaVersion`，为将来的结构迁移预留字段 |
| 结构可独立校验 | 提供不依赖引擎启动的 `validate(payload)`，用于将来上传前的结构校验 |
| 官方与 UGC 路径分离 | 官方关卡读 `levels.js`，将来 UGC 关卡读服务端；两条路径在引擎入口汇合成**同一种 payload 形态** |

一句话总结这条设计：**关卡 = 一个纯数据 payload，引擎 = 一个接收 payload 的纯函数。** 守住这一条，将来加编辑器就只是加一层外壳。

另外，经验与成就的发放规则需要提前区分（原因见平台方案第七章）：

| 内容来源 | 经验 | 成就 | 排行榜 |
|---|---|---|---|
| 官方关卡（`levels.js` 的 30 关） | ✅ 发放 | ✅ 计入 | ✅ 进入 match3 排行 |
| UGC 关卡（未来） | ❌ 不发 | ❌ 不计 | ❌ 不进 |

## 五、无尽模式设计

### 5.1 规则

- **无时间限制、无步数限制**，玩家自由结算
- 界面常驻「结束并结算」按钮，点击后弹出结算面板（本局分数 / 最高连锁 / 消除总数 / 用时）
- 结算即上报分数，进入排行榜
- **棋盘固定为标准矩形（8×8，不挖洞、不分仓）**：排行榜要求所有玩家面对同一棋盘，随机异形会破坏分数可比性。这也恰好构成了与闯关模式的显著差异——闯关玩形状，无尽玩纯粹的消除与连锁

### 5.2 难度递增（按累计分数分档）

| 累计分数 | 元素种类 | 得分倍率 | 每步有效分 | 说明 |
|---|---|---|---|---|
| 0 ~ 50,000 | 4 | ×0.5 | 365 | 起步，连锁极易触发，每分打对折 |
| 50,000 ~ 150,000 | 5 | ×1.2 | 377 | 开始需要看两步 |
| 150,000 ~ 200,000 | 6 | ×2.2 | 396 | 基准难度 |
| 200,000 ~ 300,000 | 7 | ×3.2 | 451 | 每分更值钱 |
| 300,000 以上 | 8 | ×3.8 | 498 | 上限，每步价值最高 |

按每步约 2 秒估算，到 5 色约 4.6 分钟、6 色约 13.4 分钟、7 色约 17.6 分钟，满 8 色累计约 25 分钟。

**为什么要有「得分倍率」**：颜色数越少越容易连锁，实测每步平均得分（8×8 标准盘、随机选可行步、每档 24 局）：

| 4 色 | 5 色 | 6 色 | 7 色 | 8 色 |
|---|---|---|---|---|
| 730 | 314 | 180 | 141 | 131 |

差值极不对称——**少 2 色得分高 4 倍，多 2 色只低 27%**。若不做补偿，4 色阶段会几步冲过升档门槛，一进 8 色分数几乎不涨，排行榜也会被早期 4 色的高分占满。

倍率按上表反向补偿，把「每步有效得分」排成 365 → 377 → 396 → 451 → 498 的递增序列：**颜色越多越难连锁，但每分越值钱**。

倍率的整体量级由「门槛 ÷ 目标时长」反推：门槛共 30 万分，要压在 25 分钟（约 750 步）内走完，各档有效得分就得落在 350~500 区间。**改门槛就必须等比改倍率**，否则时长会跟着变（反过来也成立——两者数学上等价，只是玩家看到的数字大小不同）。

倍率表定义在 `config.js` 的 `COLOR_SCORE_MULTIPLIER`，由 `board.js` 依据 `payload.colorScaling` 决定是否启用——**闯关模式不启用**（关卡颜色数逐关指定，目标值已按真实得分标定）。倍率上调后单步极值涨到约 1.25 万，`server/config.js` 的反刷分上限须同步复核（见 9.4）。

### 5.3 计分

- 连锁倍率：第 n 次连锁为 `1 + 0.5 × (n − 1)`，上限 ×5
- 条状 / 炸弹按波及方块数单独计分
- 连击（同一回合内多次连锁）额外加成
- 无尽模式在以上基础上再乘以「颜色数得分倍率」（见 5.2）

### 5.4 必须配套处理的两个问题

**问题一：不限时会导致排行榜被挂机刷分。**

上报时必须同时带 `moves`（操作次数）与 `durationMs`（时长），服务端做合理性校验（见 9.4），超限不入榜。否则无尽榜第一页很快会被脚本占满。

**问题二：无限长的一局，刷新即全丢。**

局内状态落 localStorage（`match3Session`），刷新后可续玩。只存最高分会让长局玩家体验很差。

### 5.5 无尽三色模式（爽局）

**定位：主打爽快感，不做难度曲线。** 固定 3 色，玩法的变化来自「连锁越接越长」，而不是颜色数变多。

| 维度 | 标准无尽 | 无尽三色 |
|---|---|---|
| 棋盘 | 8×8 | 8×8 |
| 元素种类 | 4 起步，按分数升到 8 | **固定 3，不升档** |
| 得分倍率（5.2） | 启用 | **不启用**——分数不被缩放，保留最原始的爽感 |
| 榜单 / 经验 | 各自独立 | 各自独立 |

固定 3 色为什么能一直玩：3 色下几乎每一步都能消，连锁自然变长，单步得分从 4 色的数千量级跃到上万量级。难度的唯一来源变成「这波连锁能接多长」，而不是「还找不找得到可行步」。

实测（8×8 标准盘、人类水平走子、每档 12 局 × 120 步）：

| 颜色 | 每步均分 | 单步最高 |
|---|---|---|
| 3 | 16,597 | 151,225 |
| 4 | 2,416 | 32,815 |
| 5 | 802 | 7,085 |

3 色是 4 色的 **6.9 倍**——量级差太大，所以成绩必须与标准无尽**三层隔离**，否则三色局的分数会把标准无尽的榜单与最高分成就一起顶满：

| 层 | 标准无尽 | 无尽三色 |
|---|---|---|
| 客户端存档键 | `match3Best` / `match3Session` | `match3BestEndless3` / `match3SessionEndless3` |
| 账号字段 | `highScore` / `maxCombo` | `highScore3` / `maxCombo3` |
| 协议字段 | `progress.endless` | `progress.endless3` |
| 经验除数 | `endlessExpPerScoreDivisor` | `endless3ExpPerScoreDivisor` |
| 反刷分上限 | `maxScorePerMove` | `endless3MaxScorePerMove` |

还有一处隔离：三色爽局的分数**不计入** `games.match3.totalScore` / `stats.totalScore`（服务端按 `isEndless3` 判定的 `countsToTotals`），否则它会靠单局数百万分把累计总分独占。

实现上，标准无尽与三色爽局**共用 `mode-endless.js` 一份渲染流程**，全部差异集中在文件顶部的 `VARIANTS` 表；将来再加同类变体只需往表里加一项。

注：`ENDLESS3.colors = 3` 低于 `COLOR_LIMITS.min`（那是**关卡**校验的下限，避免关卡被设计得太容易连锁），本模式是有意为之，且无尽不走关卡校验，两者不冲突。

### 5.6 肉鸽试炼（娱乐玩法）

**定位：一轮一段 run 的限步冲层。** 与无尽类「单盘长跑」相反，肉鸽每层重建棋盘，强度靠层间祝福累积。

**核心循环**

| 环节 | 规则 |
|---|---|
| 每层开局 | 重新生成 8×8 标准盘，基准 10 步（每 2 层再多 1 步），元素 6 色起 |
| 过关 | 限步内本层得分 ≥ 该层目标分；达标即锁盘，本层不再耗步 |
| 层间 | 从祝福池三选一，祝福在本轮内累计并作用于后续每层 |
| 结束 | 步数耗尽仍未达标即本轮结束；结算「到达层数 + 本轮总分」 |
| 续存 | **不做**局内续存——肉鸽一轮是连续 run，刷新即放弃（无尽模式才需要续玩） |

**目标分与步数公式**（`perks.js` 的 `goalOf` / `floorOptions`，config 只给系数）

```
目标分   = baseGoal × goalGrowth^(层数-1) × (1 + perkGoalWeight × (层数-1)) × (1 - goalCut)
本层步数 = movesPerFloor + 祝福加成 + floor((层数-1) / movesPerFloorStep)
```

**祝福池**（`perks.js` 的 `PERKS`，数据驱动：加一条数据即加一种祝福）

| 祝福 | 效果 | 上限 | 类别 |
|---|---|---|---|
| 🎒 补给包 | 每层起手步数 +2 | 3 | 成长 |
| 🎨 极简主义 | 元素种类 −1（最低 4 色） | 2 | 成长 |
| 💎 熟练手法 | 得分 ×1.25 | 6 | 成长 |
| 🧨 军火库 | 每层开局送 3 个条状 | 3 | 成长 |
| 💣 爆破专家 | 每层开局送 2 个炸弹 | 3 | 成长 |
| 🌈 彩球礼物 | 每层开局送 2 个彩球 | 2 | 成长 |
| 🧭 侦察报告 | 目标分 −18% | 4 | 成长 |
| 🛡 免死金牌 | 步数耗尽时补 3 步继续本层（一次性） | 2 | 工具 |
| 🔄 备用洗牌 | 每层免费洗牌 +1 次 | 3 | 工具 |

前 2 次三选一只出「成长」类（`friendlyPicks`）——模拟标定时观察到开局连出保命/工具牌会直接导致第 2~3 层强度不足翻车。

**数值标定**（`client-v2/tests/match3-rogue-balance.mjs`，直接 import 产品代码里的公式，改数值前先重跑）

收敛到 `baseGoal 900 / goalGrowth 1.28 / movesPerFloorStep 2 / perkGoalWeight 0.1 / 10 步起 / 6→4 色`。16 次 run（上限 35 层）实测：**中位第 22 层、p25 第 21 层、最低 17 层、首层 0 次翻车**，全程达成率（可达分 ÷ 目标分）落在 1.2~6.9 倍；模拟用的是随机走子，真人水平会更高几层。线上实测一局：**23 层 / 80.7 万分 / 12:47**（熟练手法 6 张、侦察报告 4 张、极简主义 2 张、爆破专家 3 张、彩球礼物 2 张），与标定吻合。

**关键设计：层数成长来源。** 棋盘参数（颜色数 / 得分倍率 / 特殊元素）只由祝福决定，祝福叠满后每层的「可达分平台」就固定了。若没有随层数增长的来源，目标分的指数曲线迟早越过这条平台，run 必然在固定层数猝死、且后期分数横盘——这正是实测反馈「buff 不够强力、后面分数上不去」的根因：无层数成长时，4 色 ×2.07 的 build 从第 10 层起每层可达分稳定在 2 万上下，第 15 层目标 46,776 直接打不动。解法是每 `movesPerFloorStep` 层多发 1 步，让可达分随层数线性上涨（实测第 1 层 1,545 → 第 20 层约 16 万），玩家每层都能看到分数变高。相应地，`movesPerFloorStep` 取 2 而非 3：步数增长太慢时会出现「首个三选一前棋盘参数还弱、第 2~3 层暴死」的极端局。

标定过程中被否掉的几版：

- `baseGoal 1500` 太贴 6 色 10 步的中位分（1750），「脸黑停在第 2~3 层」的 run 大量出现；
- `goalGrowth 1.15 / 1.19 / 1.22` 配层数成长后过松（中位 25~29 层，全部打满模拟上限），说明目标曲线被削得太狠；
- 「连锁倍率上限」祝福实测在 6 色 / 4 色下**完全无效**（上限 5/7/9/11 的中位分都是 1755 / 7130），只保留引擎参数、不进祝福池。

**硬约束：元素种类下限 4 色**（`ROGUE.minColors`）。3 色每步均分 66,187 比 4 色的 5,295 高约 10 倍，若允许降到 3 色，「极简主义」会变成压倒性最优解且分数尺度失控——3 色留给无尽三色。

**成绩隔离**（沿用 5.5 的三层思路，`mode='rogue'`）

| 层 | 字段 |
|---|---|
| 客户端存档键 | `match3BestRogue`（`{ maxFloor, highScore }`） |
| 账号字段 | `rogueMaxFloor` / `rogueHighScore` |
| 协议字段 | `progress.rogue` |
| 经验除数 | `rogueExpPerScoreDivisor`（800） |
| 反刷分上限 | `rogueMaxScorePerMove`（60,000/步） |

与 5.5 一致，肉鸽的分数**不计入** `games.match3.totalScore` / `stats.totalScore`，`maxCombo` 也不并进共享的无尽最高连锁（`countsToTotals` / `maxCombo` 均按 `isRogue` 判定）。

**实现落点**：`mode-rogue.js` 只做状态机与渲染，数值与推导全在 `perks.js` / `config.js`（`ROGUE`）；board 侧为肉鸽新增了三个参数：`scoreMult`（得分倍率）、`cascadeMax`（连锁倍率上限）、`specials`（开局注入特殊元素），以及 `addMoves` / `shuffle` 两个方法。

**数值可见性**：`mode-rogue.js` 的 `bonusStats(bonus, floor)` 把加成折算成该层实际生效的数值（口径复用 `floorOptions` / `goalOf`，不另立一套），对局中、三选一时、结算后都展示；三选一卡片再用 `perkDelta` 给出「本层 → 下一层」的原值 → 新值，让玩家能直接看到每个祝福的收益（详见七、UI 结构）。

### 6.2 设计要点

| 项 | 方案 |
|---|---|
| 引擎与渲染分离 | `grid` / `match` / `special` / `cascade` / `deadlock` 均为纯逻辑，不碰 DOM，可在控制台或 Node 中独立跑用例验证 |
| 渲染方式 | DOM + CSS `transform` / `transition`，格子**绝对定位**（异形棋盘不能靠统一的 grid 布局），棋盘容器按 mask 包围盒计算尺寸；不用 Canvas |
| 动画编排 | `async/await` 串 Promise：交换 150ms → 消除 200ms → 下落 250ms → 补充 → 下一轮连锁；动画期间锁输入 |
| 棋盘生成 | `initial` 为空时按 `colors` 随机生成，并强制保证「无现成三连」+「至少一个可行交换」；配套开发期关卡校验脚本（见风险清单） |
| 状态管理 | 对局状态放模块内局部 state（对齐贪吃蛇的做法）；只有跨页面数据（关卡进度、最高分）走 `store` + `api` |
| 主题适配 | 所有颜色走 CSS 变量，自动跟随现有主题切换 |

### 6.4 配置化原则

**所有数值、开关、阈值一律不写死在逻辑里。** 按归属分三层：

| 层 | 位置 | 放什么 | 例子 |
|---|---|---|---|
| 游戏配置 | `client-v2/src/games/match3/config.js` | 全局玩法参数与表现参数 | 棋盘尺寸上下限、元素种类上下限、各类消除分值、连锁倍率曲线、无尽难度分档表、动画时长 |
| 关卡配置 | `client-v2/src/games/match3/levels.js` | 与单关相关的数值 | 棋盘尺寸、mask、元素种类、步数、目标、障碍、星级阈值 |
| 服务端配置 | `server/config.js` 的 `match3Rewards` | 奖励与风控 | 经验公式参数、反刷分阈值 |

硬性要求：

- 逻辑代码里**不出现魔法数字**——`0.5`（倍率步长）、`150`（动画时长）、`50000`（难度分档门槛）这类必须命名并抽到配置
- 无尽模式的难度分档、连锁倍率曲线**必须是数据表**，不是 if-else 链；将来调平衡只改数据、不改逻辑
- 动画时长、连击反馈等表现参数同样进配置，便于统一调整手感
- 配置项命名自解释，改配置不需要读逻辑代码

一句话：**逻辑只负责"怎么算"，配置负责"算多少"。**

### 6.5 引擎的单元验证方式

引擎层全部是纯逻辑、不碰 DOM，因此用 Node 直接跑用例验证，不依赖浏览器。项目根 `package.json` 是 CommonJS（服务端用 `require`），无法直接 `import` 客户端的 `.js`，需在 `client-v2/` 下放一个 `package.json` 标记该子树为 ESM：

```json
{ "type": "module" }
```

该文件只影响 Node 的模块解析，浏览器始终按 `<script type="module">` 处理，对运行时零影响。用例放在 `client-v2/tests/`，通过 `node client-v2/tests/match3-engine.test.js` 执行。

## 七、UI 结构

```
#/match3
├─ 模式选择（入口）
│   ├─ 🍭 闯关 —— 第 N 关 / 累计 ★
│   ├─ ♾ 无尽 —— 最高分 / 最高连锁
│   └─ 🎪 娱乐 —— 二级菜单入口
│       └─ 娱乐模式（不设关卡与目标）
│           ├─ 🧨 无尽三色 —— 最高分 / 最高连锁（独立成绩）
│           └─ 🎲 肉鸽试炼 —— 最深层数 / 最高分（独立成绩）
├─ 关卡列表（按章节分组的网格，含星数与锁定态）
└─ 对局界面
    ├─ HUD：步数 或 分数 / 目标进度 / 最高连锁
    ├─ 棋盘（形状与尺寸由关卡决定；无尽模式为标准矩形）
    └─ 操作区：暂停、结束并结算（仅无尽）、重开、积分详情
```

娱乐模式是二级菜单：定位为「不设关卡与目标的爽快玩法」，当前收「无尽三色」与「肉鸽试炼」，
后续同类玩法（如限时、特殊棋盘）直接加进这一层，主菜单保持三项不变。

肉鸽试炼另有几处专属界面：层间的三选一祝福卡（`.m3-perks` / `.m3-perk`）、
已获祝福条（`.m3-perks-strip`）、页内结算卡（`.m3-result--inline`，与无尽类盖在棋盘上的浮层结算区分）、
以及**加成数据面板**（`.m3-stats`，对局中与三选一界面都显示）。

数据面板把祝福折算成「该层实际生效的数值」——起手步数 / 元素种类 / 得分倍率 / 目标分减免 /
开局附赠特殊元素 / 免死 / 免费洗牌，口径直接取自 `perks.js` 的 `floorOptions`；三选一卡片上再列出
「原值 → 新值」的变化（含每 2 层 +1 步的层数成长），让「祝福到底带来了多少提升」是看得见的数字，
而不是只能靠手感。

## 八、存档结构

| 键 | 内容 | 说明 |
|---|---|---|
| `match3Progress` | `{ maxLevel, stars: { 关号: 星数 } }` | **闯关进度以服务端为唯一真相**，本地只是服务端进度的缓存 |
| `match3Best` | `{ highScore, bestCombo }` | 标准无尽，本地与服务端取 max 合并 |
| `match3Session` | `{ mode, board, score, moves, level, ts }` | 标准无尽，用于刷新后续玩 |
| `match3BestEndless3` | `{ highScore, bestCombo }` | 无尽三色，与 `match3Best` 完全隔离（见 5.5） |
| `match3SessionEndless3` | 同上结构 | 无尽三色局内续存 |
| `match3BestRogue` | `{ maxFloor, highScore }` | 肉鸽试炼，与其它模式完全隔离（见 5.6）；肉鸽一轮是连续 run，故**无** session 键 |

冲突处理原则：**只有展示用的最佳分取 max 合并**；闯关进度（解锁与星数）完全由服务端下发覆盖本地，
本地不作为进度来源。原因是进度一旦本地领先，9.4 的「关卡推进」校验会一直判跳关，
而 max 合并又让本地永远领先——玩家自此拿不到经验、也进不了闯关榜，无法自愈。
代价是未登录 / 断线时打的通关不计进度（界面上会提示），且换设备后只能继续服务端已记录到的关卡。

C→S  match3_game_end       { mode, level?, floor?, score, maxCombo, moves, durationMs,

### 9.3 数据模型

沿用贪吃蛇的既有形状，不新造结构：

```js
// account.games.match3 —— 只放不随关卡数增长的汇总标量
{
  totalGames: 0,
  highScore: 0,        // 标准无尽最高分
  highScore3: 0,       // 无尽三色最高分（与 highScore 隔离，见 5.5）
  rogueMaxFloor: 0,    // 肉鸽试炼最深到达层数（与其它模式隔离，见 5.6）
  rogueHighScore: 0,   // 肉鸽试炼最高本轮总分
  totalScore: 0,       // 仅累计闯关与标准无尽，三色爽局与肉鸽不计入
  maxCombo: 0,         // 标准无尽单局最高连锁（三色与肉鸽都不并入）
  maxCombo3: 0,        // 无尽三色单局最高连锁
  maxLevel: 0,         // 闯关模式已通关最高关
  totalStars: 0,       // 累计星数（由逐关星表推导，便于排行榜 / 成就免二次读取）
  lastPlayedAt: null
}

// account.stats.match3Games
{ totalGames, totalScore, highScore, maxLevel, totalStars }

// data/match3/<accountId>.json —— 逐关明细独立存储
{ userId, stars: { 关号: 星数 } }
```

**注意**：结构里**不包含** `wins` / `losses` / `draws`（与 `games.snake` 一致）。

**为什么逐关星表要单独存**：星表是唯一随关卡数线性增长的字段（30 关约 0.5 KB，1000 关就是十几 KB），
而账号文件是整体读写的——`dataStore.writeOne` 每次都用 `JSON.stringify(整个记录)` 重写文件，
登录、加经验、发邮件、聊天任何一次账号写入都会把星表一起序列化重写一遍。
拆成独立集合（与 `inventories` / `mails` 同一套 `splitByIdCollections` 机制）后，
随关卡增长的部分不再进账号文件，排行榜、成就、跳关校验读的都是账号里的汇总标量，零改动。
老账号里残留的 `games.match3.stars` 由 `AccountManager.getMatch3Stars` 在首次读取时
按关取最高合并到独立文件、并从账号中删除（惰性迁移，无需启动时全量扫描）。

### 9.4 反刷分校验

在 `match3_game_end` 内执行，任一不通过则：记日志 → 不发经验 → 不入榜。

| 校验 | 规则 |
|---|---|
| 分数与步数 | `score ≤ moves × 本模式单步上限`（闯关 / 标准无尽 25000；无尽三色 60000；肉鸽试炼 60000） |
| 分数与时长 | `durationMs ≥ moves × minMsPerMove` |
| 关卡推进 | `mode === 'level'` 时 `level ≤ maxLevel + 1`（防跳关） |

`maxScorePerMove` 按「客户端缩放后的单步有效分」定：实测极值为 4色 8948 / 5色 12498 / 6色 5148 / 7色 4961 / 8色 5871，取 25000 留约 2 倍余量，避免正常长连锁被误杀。**改 `COLOR_SCORE_MULTIPLIER` 后必须回来看这一项**（倍率抬一倍，此项也要跟着抬，否则正常玩家会被判违规）。

`endless3MaxScorePerMove` 单独放宽到 60000：三色爽局不分档、不缩放，连锁极长，实测人类水平每步均分约 16,600、单步最高约 15 万，沿用 25000 会把正常玩家误判为刷分（见 5.5）。

`rogueMaxScorePerMove` 同样取 60000：肉鸽的「极简主义」会降到 4 色、「熟练手法」还能叠到 ×3.81（×1.25 / 最多 6 张），单步得分比标准无尽高一个量级（见 5.6）。

### 9.5 经验公式

在 `server/config.js` 新增（对齐现有 `config.snakeRewards` 的写法）：

```js
match3Rewards: {
  baseExp,
  expPerScoreDivisor,          // 闯关模式经验换算除数
  endlessExpPerScoreDivisor,   // 标准无尽经验换算除数（无尽一局得分可达数万分，须用更小的除数）
  endless3ExpPerScoreDivisor,  // 无尽三色经验换算除数（一局可达数百万分，是标准无尽的约 20 倍尺度）
  rogueExpPerScoreDivisor,     // 肉鸽试炼经验换算除数（整轮累计总分约数万，量级接近标准无尽）
  starBonus,                   // 闯关模式按星级额外加成
  maxScorePerMove,
  endless3MaxScorePerMove,
  rogueMaxScorePerMove,
  minMsPerMove
}
```

公式沿用贪吃蛇：`exp = baseExp + floor(score / 模式对应除数)`。

闯关与无尽分开定除数的原因：闯关一局得分在几千量级（30 分/方块），无尽一局可打到数万分，
两者分数尺度差约 10 倍。若共用同一除数，无尽模式的单位时间经验会被严重稀释
（实测：无尽一局 3.4 万分仅得 144 经验，约 5 经验/分钟，而贪吃蛇/五子棋为 20-60 经验/分钟）。

三色爽局单独再定一个除数（1200）的原因同理：它的分数尺度比标准无尽再高约 20 倍，
取 1200 让它的**经验/分钟**与标准无尽大致同档，不因为分高就爆经验（分高但更爽，不该同时更赚）。

肉鸽试炼的除数取 800：整轮累计总分约 80~120 万（模拟中位 22 层约 120 万；实测一局 23 层 80.7 万分，
换算基础经验 1039），即约 1000~1500 经验/轮，低于标准无尽跑满一轮（30 万分 → 5000 经验），
与它「一轮时长更短」的定位相符。

## 十、v2-only 兼容性核实与硬约束

### 10.1 核实结论

消消乐只写在 v2，但账号数据存在同一服务端，v1 用户也会拿到带 `match3` 字段的账号。逐处核实如下：

| v1 触点 | 行为 | 需要处理 |
|---|---|---|
| 导航栏游戏按钮（`client/index.html` L3945 附近） | 硬编码，不渲染 match3 | 否 |
| 排行榜类型按钮（L4151） | 硬编码，不显示 match3 | 否 |
| 个人资料游戏统计（L6443 固定数组 `['gobang','chinese-chess','go','snake']`） | 不显示 match3 | 否 |
| gameType 中文名映射（L13669） | 无 match3 条目，但调用路径不会走到 | 否 |
| 成就列表 | 服务端全量返回，v1 可能列出 match3 成就 | **是**：徽章 SVG 必须存在 |
| 对战历史 / 回放（v2 `features/replay/index.js` 按 gameType 分支，未知类型无兜底） | 未知类型会返回空 | **是**：消消乐不得进入历史 |

**结论**：v1 不会因此崩溃（其游戏列表、排行榜、统计均为硬编码固定数组），只需保证徽章资源存在、且消消乐不进历史体系。

### 10.2 硬约束（写代码前必须遵守）

1. **`games.match3` 结构对齐 `games.snake`**，不引入 `wins` / `losses` / `draws`。
   原因：总榜是把所有游戏的 `wins` 累加计算的，加入胜负字段会污染总榜数据。
2. **不调用 `updateGameStats`**（`AccountManager.js` L1323）。那是棋类胜负统计的入口，消消乐（尤其无尽模式自由结算）没有胜负概念。
3. **不写入 `games` 集合（对战历史）**。
   贪吃蛇走了这条路——`saveSnakeGameRecord` 里有 `dataStore.add('games', record)`（`GameManager.js` L1314），代价是回放模块必须为它加专门的 Canvas 分支。消消乐没有回放价值，不入历史可以直接省掉回放、观战、对战历史一整条链路。
4. **`getLeaderboard` 必须显式加 match3 分支**。
   `AccountManager.getLeaderboard` 对未知类型会 fallback 到 `games[type].wins`，而 match3 没有 `wins` → 所有人 0 分，榜单等于不存在。参照 L551-L555 与 L569-L571 的 snake 分支写法。
5. **新成就的 `badge` 必须有对应 SVG 文件**放在 `server/assets/badges/`。

## 十二、分阶段实施计划

| 阶段 | 内容 | 验收 |
|---|---|---|
| P1 | 引擎全套：`grid` / `match` / `special` / `cascade` / `deadlock` | 控制台跑用例，形态识别（L/T/5/4/3）、特殊元素级联、连锁与死局判定全部正确 |

| P6 | 打磨：移动端滑动、主题变量适配、新手引导、（可选）道具与商城联动 | 手机可玩，主题不串色 |

每个阶段完成后都是可独立运行的版本。

## 十三、风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| 特殊元素的级联触发写成死循环 | 页面卡死 | while 队列 + 触发次数上限保护，P1 阶段用例覆盖 |
| 无尽模式不限时被脚本刷分 | 排行榜失效 | 9.4 的三条校验必须和上报接口同时上线，不能延后 |
| 成就条件求值逻辑不支持新字段 | 成就无法解锁 | 实现时同步在 `checkAchievements` 补条件分支（见 9.6 注意项） |
| 洗牌后仍为死局 | 玩家卡死 | 洗牌后强制复检，复检失败则重新洗牌（设上限） |
| 动画与逻辑耦合导致改一处崩一处 | 维护困难 | 引擎层不碰 DOM，动画只在 `board.js` 编排 |
| 前期把消消乐塞进统一游戏大厅 | 结构别扭、返工 | 已决策走独立导航项，不并入大厅 |
| 高自由度棋盘容易配出不可通关的关卡 | 卡关、玩家流失 | 增加开发期关卡校验脚本：检查 mask 合法性、目标是否可达、初始无三连且有可行步 |
| 异形棋盘只靠肉眼验证容易漏错 | 上线后才发现形状或下落错位 | P1 用例必须覆盖挖洞与分仓棋盘；P2 对矩形 / 异形 / 分仓各跑一次 |
| 分仓棋盘整体洗牌破坏其他区域局面 | 玩家体验受损 | 洗牌与死局判定均以「区域」为粒度（见 3.6） |
