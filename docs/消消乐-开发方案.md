## 一、方案概述

### 1.1 要做什么

在 `client-v2/` 中新增一个三消游戏「消消乐」，包含两种主模式 + 一个娱乐层：

- **闯关模式**：步数制，按关卡目标与星级推进
- **无尽模式**：无时间无步数限制，玩家自由结算，按分数排名
- **娱乐模式**：二级菜单，放不设关卡与目标的玩法，当前有「无尽三色」（5.5）与「肉鸽试炼」（5.6），成绩各自独立

### 1.2 为什么只做 v2

- 消消乐是**纯单人玩法**，不涉及匹配、房间、悔棋、观战、回放等联机协议
- v2 是原生 ES Modules + 无构建，新增一个游戏模块的边际成本远低于改动 `client/index.html`（12672 行单文件）
- 与既有策略一致：**v1 冻结只维护，v2 主力开发**；v1 未来会被 v2 全量替代
- 参考对象是现有的贪吃蛇（同为"单人本地逻辑 + 结束后上报"），是现成的最佳模板

### 1.3 不做什么

| 不做 | 原因 |
|---|---|
| v1 客户端实现 | v1 结构不适合大改，且未来会被 v2 替代 |
| 联机对战 / 观战 / 回放 | 玩法性质不需要，且能省掉一整条链路 |
| 个人资料页展示消消乐进度 | 控制改动面，入口为导航项 + 排行榜 + 成就 |
| 特殊元素两两组合（条状+条状=十字等） | 分支数量是 n² 级别，v1 只保留"彩球 + 任意" |
| 关卡编辑器与创意工坊 | 未来展望，等消消乐玩法稳定后再做（见 `关卡平台-设计方案.md`）；首版只满足 UGC-ready 约束（见 4.5） |

## 三、核心玩法设计

### 3.1 核心循环

```
玩家交换相邻方块
      ↓
匹配三连及以上（横/竖同色，含 L/T 形）
      ↓
消除、下落、顶部补充
      ↓
连锁判定 ──还能连锁──→ 回到匹配
      ↓ 无连锁
回合结束（无可行步则重排棋盘）
```

**连锁（Cascade）是这个游戏的核心爽点**，也是无尽模式的主要得分来源。

### 3.2 棋盘自由度与参数

棋盘**不固定尺寸也不固定形状**，形状与参数逐关配置——这是关卡设计的主要表达手段。

**自由度分层**

| 层级 | 形态 | v1 是否支持 |
|---|---|---|
| L0 | 任意矩形（如 7×8、9×10） | ✅ |
| L1 | 异形：在矩形范围内挖洞，形成菱形 / 十字 / 环形等奇怪排列 | ✅ |
| L2 | 分仓多区域：洞把棋盘切成互不相连的几块，各自独立下落 | ✅ |
| L3 | 可变重力方向（向上 / 向左掉落）、传送门、多层棋盘 | ❌ 预留，v1 不做 |

关键实现结论：**L1 与 L2 不需要写两套逻辑**。只要下落按「同一列内的连续可玩段」处理，洞与分仓就自然成立——洞把列切断成多段，每段独立下落即可。

**参数范围**（逐关可配）

| 参数 | 范围 | 默认 |
|---|---|---|
| 行 × 列 | 8 ~ 12 行 × 8 ~ 10 列 | 8 × 8 |
| 可玩格子上限 | ≤ 120 | — |
| 元素种类 | 4 ~ 8 | 6 |
| 重力方向 | v1 固定 `down` | `down` |

元素种类的取舍：少于 4 种太容易连锁，多于 8 种挫败感强。闯关模式第 1 章（完整矩形）用 5 种，第 2 / 3 章（挖洞 / 分仓的碎格子棋盘）压到 4 种——碎格子棋盘没有完整行列可借力，颜色一多就频繁出现「全盘无可行步 → 只能靠系统洗牌」（实测 6 色时有 6 关平均每 60 步要洗 3~7 次牌，降到 4 色后基本归零），目标值已按 4 色重新标定。无尽模式随分数分档从 4 提到 8（见 5.2），并用「颜色数得分倍率」抵消低颜色数的得分红利。

**分仓棋盘的一处特别注意**：如果某个区域完全没有可行交换，不能对整个棋盘洗牌（会破坏其他区域的局面），洗牌逻辑要以「区域」为粒度（见 3.6）。

**颜色权重（可选参数）**：开局铺色与连锁补充都走 `cascade.js` 的 `pickColor(rng, colors, weights)`，`weights` 为按颜色下标排列的权重数组，缺省项按 1 计。不传权重时它逐位等价于 `1 + rng.int(colors)`——这是硬约束，历史关卡与所有非肉鸽模式的复现性都依赖它（见 4.5）。加权只影响「补充什么颜色」，不改变匹配 / 计分规则，因此纯关卡模式不启用；它目前的唯一使用者是 5.6 的肉鸽祝福「同色磁石」。

### 3.3 消除规则

- 横或竖方向同色 3 连及以上触发消除
- 匹配判定分两趟扫描：先扫全部行，再扫全部列，O(n²)
- **洞会自然切断连线**：扫描时跳过不可玩格子，因此异形棋盘不需要任何特判——挖了洞，连线自己就断了
- **形态识别优先级**：先识别 L/T 形（交叉），再识别直线 5 连，再识别直线 4 连，最后才是普通 3 连

### 3.4 交换规则

- 只接受**能形成消除**的交换，非法交换播放回弹动画
- 这是三消手感的关键，必须做，不能省

### 3.5 特殊元素

| 触发形态 | 生成元素 | 效果 |
|---|---|---|
| 4 连（横） | 横条 | 消除整行 |
| 4 连（竖） | 竖条 | 消除整列 |
| 5 连直线 | 彩球 | 消除全场同色 |
| L / T 形（横竖各 ≥3 共用一格） | 炸弹 | 消除 3×3 范围 |

三条必须定死的规则：

1. **生成位置**：特殊元素生成在玩家**交换的那一格**（行业标准做法，手感最好）
2. **级联触发**：特殊元素被波及消除时立即触发其效果，效果再波及到其他特殊元素则继续触发。用 while 队列处理，并设置触发上限以防死循环。**彩球是例外**：条状 / 炸弹的爆炸不波及彩球，扫到也原地保留（不触发、不消耗），彩球只在玩家主动拿它去交换时才结算
3. **组合玩法**：v1 只保留「彩球 + 任意」一条，其余组合不做
   - 彩球 + 普通方块 / 彩球：清除全场同色 / 清空全盘
   - 彩球 + 条状 / 炸弹：把该特殊效果**复制给全部同色棋子**，再逐颗触发（复制保留颜色）

### 3.6 死局处理

- 无任何可行交换时自动洗牌
- **洗牌后必须复检**，避免洗出新的死局
- 洗牌与复检都**只在可玩格子内**进行
- **分仓棋盘以「区域」为粒度**：某个区域死局时只重排该区域，不能让整个棋盘一起洗，否则会破坏其他区域的局面

### 3.7 棋盘数据结构

**棋盘本身要携带形状信息**，不能只是一个二维数组：

```js
// 可玩性判断
grid.isPlayable(r, c)        // mask[r][c] === 1

// 按列拆成若干连续可玩段，供下落逻辑使用
// 洞把一列切成多段，每段独立下落 —— 异形与分仓由此自然支持
grid.columnSegments(c)       // → [{ from, to }, ...]

// 区域（连通块）划分，供分仓洗牌与死局判定使用
grid.regions()               // → [ Set<cellIndex>, ... ]

// 坐标映射（渲染用，异形棋盘不能靠统一 grid 布局）
grid.toPixel(r, c)           // → { x, y }
```

单元格从纯数字升级为对象：

```js
{ color: 1..8, special: null | 'row' | 'col' | 'bomb' | 'rainbow' }
```

## 四、闯关模式设计

### 4.1 规则

| 项 | 规则 |
|---|---|
| 结束条件 | 步数制，每关固定步数，用完即结算 |
| 目标类型 | ① 得分达标 ② 收集指定颜色 N 个 ③ 清除全部障碍（冰块/石头/锁链） |
| 星级 | 3 星 = 通关且剩余步数 ≥ 30%；2 星 = 剩余步数 ≥ 10%；1 星 = 通关（剩余 0 步） |
| 解锁 | 通关后解锁下一关；星级用于展示与奖励 |

### 4.2 关卡数据

配置放客户端 `levels.js`（跟随版本发布，离线可玩，服务端不做配置管理）。单人游戏数值被修改可接受。

```js
{
  id: 1,
  name: '初入糖果镇',

  // 棋盘形状：逐关可变
  rows: 8,
  cols: 8,
  // 可玩格遮罩，1 = 可玩，0 = 洞；留空则整块矩形全可玩
  // 用字符串数组是为了手工设计关卡时可读（不用数数字）
  mask: [
    '11111111',
    '11111111',
    '11001111',
    '11001111',
    '11111111',
    '11111111',
    '11111111',
    '11111111',
  ],

  colors: 5,                  // 本关元素种类（可低于默认 6）
  moves: 20,                  // 步数上限
  goals: [
    { type: 'score', target: 3000 },
    { type: 'collect', color: 'red', target: 15 },
    { type: 'clearBlockers', target: 8 },
  ],
  blockers: [ { r: 3, c: 4, kind: 'ice', hp: 2 } ],
  initial: null,              // 可选：显式指定初始布局；为空则按规则生成
  gravity: 'down',            // 预留字段，v1 固定 'down'
  starScore: 3000,            // 1 星门槛
}
```

**初始化规则**：`initial` 为空时按 `colors` 随机生成，且必须满足两个约束——**棋盘上不存在现成的三连**、**至少存在一个可行交换**。这两条由生成器保证，不依赖关卡配置的正确性。

### 4.3 关卡规模

首版做 **30 关（3 章 × 10 关）**，用于验证难度曲线。

章节按棋盘形态递进，让「形状」本身成为难度与新鲜感的来源：

| 章节 | 关卡数 | 棋盘形态 | 目标 |
|---|---|---|---|
| 第 1 章 | 10 | 标准矩形为主，尺寸逐步变大 | 得分 / 收集 |
| 第 2 章 | 10 | 引入异形（挖洞：菱形、十字、环形） | 增加清除障碍 |
| 第 3 章 | 10 | 引入分仓多区域 + 混合形态 | 三类目标混用 |

**每关棋盘形状不同是设计目标，不是副作用**——这决定了关卡配置不能靠程序批量生成，必须有开发期校验（见风险清单）。

### 4.4 关卡列表 UI

按章节分组的网格，显示星数与锁定态。**不做卷轴大地图**，避免一上来就产生美术资源需求。

### 4.5 UGC-ready 约束

关卡编辑器与创意工坊属于未来展望（见 `关卡平台-设计方案.md`），**不在本方案范围内**。但为了让将来接入平台时不需要重构，首版就要满足以下约束。

这些约束**不增加额外工作量**，只是写法上的要求：

| 约束 | 要求 |
|---|---|
| payload 是纯数据 | 关卡配置只包含 JSON 可序列化的值，不含函数、类实例、DOM 引用 |
| 可从外部加载 | 引擎必须支持「传入一个 payload 直接开局」，不依赖模块内部 state 或游戏流程的既有状态 |
| 可重复加载 | 同一 payload 反复加载得到完全相同的局面，**不能有随机残留**——随机生成必须只在生成阶段发生一次（或使用可播种随机），引擎内部不得调用 `Math.random` |
| 带 `schemaVersion` | 每关携带 `schemaVersion`，为将来的结构迁移预留字段 |
| 结构可独立校验 | 提供不依赖引擎启动的 `validate(payload)`，用于将来上传前的结构校验 |
| 官方与 UGC 路径分离 | 官方关卡读 `levels.js`，将来 UGC 关卡读服务端；两条路径在引擎入口汇合成**同一种 payload 形态** |

一句话总结这条设计：**关卡 = 一个纯数据 payload，引擎 = 一个接收 payload 的纯函数。** 守住这一条，将来加编辑器就只是加一层外壳。

另外，经验与成就的发放规则需要提前区分（原因见平台方案第七章）：

| 内容来源 | 经验 | 成就 | 排行榜 |
|---|---|---|---|
| 官方关卡（`levels.js` 的 30 关） | ✅ 发放 | ✅ 计入 | ✅ 进入 match3 排行 |
| UGC 关卡（未来） | ❌ 不发 | ❌ 不计 | ❌ 不进 |

## 五、无尽模式设计

### 5.1 规则

- **无时间限制、无步数限制**，玩家自由结算
- 界面常驻「结束并结算」按钮，点击后弹出结算面板（本局分数 / 最高连锁 / 消除总数 / 用时）
- 结算即上报分数，进入排行榜
- **棋盘固定为标准矩形（8×8，不挖洞、不分仓）**：排行榜要求所有玩家面对同一棋盘，随机异形会破坏分数可比性。这也恰好构成了与闯关模式的显著差异——闯关玩形状，无尽玩纯粹的消除与连锁

### 5.2 难度递增（按累计分数分档）

| 累计分数 | 元素种类 | 得分倍率 | 每步有效分 | 说明 |
|---|---|---|---|---|
| 0 ~ 50,000 | 4 | ×0.5 | 365 | 起步，连锁极易触发，每分打对折 |
| 50,000 ~ 150,000 | 5 | ×1.2 | 377 | 开始需要看两步 |
| 150,000 ~ 200,000 | 6 | ×2.2 | 396 | 基准难度 |
| 200,000 ~ 300,000 | 7 | ×3.2 | 451 | 每分更值钱 |
| 300,000 以上 | 8 | ×3.8 | 498 | 上限，每步价值最高 |

按每步约 2 秒估算，到 5 色约 4.6 分钟、6 色约 13.4 分钟、7 色约 17.6 分钟，满 8 色累计约 25 分钟。

**为什么要有「得分倍率」**：颜色数越少越容易连锁，实测每步平均得分（8×8 标准盘、随机选可行步、每档 24 局）：

| 4 色 | 5 色 | 6 色 | 7 色 | 8 色 |
|---|---|---|---|---|
| 730 | 314 | 180 | 141 | 131 |

差值极不对称——**少 2 色得分高 4 倍，多 2 色只低 27%**。若不做补偿，4 色阶段会几步冲过升档门槛，一进 8 色分数几乎不涨，排行榜也会被早期 4 色的高分占满。

倍率按上表反向补偿，把「每步有效得分」排成 365 → 377 → 396 → 451 → 498 的递增序列：**颜色越多越难连锁，但每分越值钱**。

倍率的整体量级由「门槛 ÷ 目标时长」反推：门槛共 30 万分，要压在 25 分钟（约 750 步）内走完，各档有效得分就得落在 350~500 区间。**改门槛就必须等比改倍率**，否则时长会跟着变（反过来也成立——两者数学上等价，只是玩家看到的数字大小不同）。

倍率表定义在 `config.js` 的 `COLOR_SCORE_MULTIPLIER`，由 `board.js` 依据 `payload.colorScaling` 决定是否启用——**闯关模式不启用**（关卡颜色数逐关指定，目标值已按真实得分标定）。倍率上调后单步极值涨到约 1.25 万，`server/config.js` 的反刷分上限须同步复核（见 9.4）。

### 5.3 计分

- 连锁倍率：第 n 次连锁为 `1 + 0.5 × (n − 1)`，上限 ×5
- 条状 / 炸弹按波及方块数单独计分
- 连击（同一回合内多次连锁）额外加成
- 无尽模式在以上基础上再乘以「颜色数得分倍率」（见 5.2）

### 5.4 必须配套处理的两个问题

**问题一：不限时会导致排行榜被挂机刷分。**

上报时必须同时带 `moves`（操作次数）与 `durationMs`（时长），服务端做合理性校验（见 9.4），超限不入榜。否则无尽榜第一页很快会被脚本占满。

**问题二：无限长的一局，刷新即全丢。**

局内状态落 localStorage，刷新后可续玩；只存最高分会让长局玩家体验很差。**并且这份暂存要云同步**：换设备、清缓存、换浏览器之后仍能接着打，否则「长局」的续玩能力只保住了刷新这一种情况。

暂存 = **一份未结算的一局**，按玩法分档（`endless` / `endless3` / `rogue`），三种玩法共用同一套读写：

| 环节 | 做法 |
|---|---|
| 本地写 | 每次状态变化覆盖写同一个键（刷新即续），无节流 |
| 云端推 | `match3_save_session` 按 15s 节流；**进层 / 过关三选一 / 结算**这些关键节点 `force` 立即推 |
| 云端拉 | 随 `match3_sync_progress` 的 `sessions` 字段一起下发，落到服务端 `data/match3/<accountId>.json` 的 `sessions` 里 |
| 合并 | 与最高分不同，暂存**不取 max**——它是一份「当前进度」，同一局只可能在一个设备上往前推，故只认 `ts` 更新的那份；本地更新时反过来推回云端 |
| 结束 | 写一个带新 `ts` 的**墓碑** `{ mode, finished: true, ts }` 占住同一个键，并把它推上云端（不是删键）：既不会被当成可续玩的局，又能压掉别的设备上那份旧暂存 |
| 过期 | 超过 7 天（`match3Session.maxAgeMs`）视为过期：既不提示续玩，也不参与与云端比新旧 |

服务端只做边界校验与保管，不解释内容：`variant` 必须在白名单内、`session.mode` 必须与 `variant` 一致、序列化后不超过 32KB（`match3Session.maxBytes`）。这样暂存不是「客户端说了算」的可执行数据，服务端也不需要跟着玩法改版而改。

**已知取舍**：暂存只在「同一账号」内云同步，未登录时只在本地；`match3Session` 不在 `server/modules/runtimeConfig.js` 的可调项白名单里，改这组参数需要重启服务端。

### 5.5 无尽三色模式（爽局）

**定位：主打爽快感，不做难度曲线。** 固定 3 色，玩法的变化来自「连锁越接越长」，而不是颜色数变多。

| 维度 | 标准无尽 | 无尽三色 |
|---|---|---|
| 棋盘 | 8×8 | 8×8 |
| 元素种类 | 4 起步，按分数升到 8 | **固定 3，不升档** |
| 得分倍率（5.2） | 启用 | **不启用**——分数不被缩放，保留最原始的爽感 |
| 榜单 / 经验 | 各自独立 | 各自独立 |

固定 3 色为什么能一直玩：3 色下几乎每一步都能消，连锁自然变长，单步得分从 4 色的数千量级跃到上万量级。难度的唯一来源变成「这波连锁能接多长」，而不是「还找不找得到可行步」。

实测（8×8 标准盘、人类水平走子、每档 12 局 × 120 步）：

| 颜色 | 每步均分 | 单步最高 |
|---|---|---|
| 3 | 16,597 | 151,225 |
| 4 | 2,416 | 32,815 |
| 5 | 802 | 7,085 |

3 色是 4 色的 **6.9 倍**——量级差太大，所以成绩必须与标准无尽**三层隔离**，否则三色局的分数会把标准无尽的榜单与最高分成就一起顶满：

| 层 | 标准无尽 | 无尽三色 |
|---|---|---|
| 客户端存档键 | `match3Best` / `match3Session` | `match3BestEndless3` / `match3SessionEndless3` |
| 账号字段 | `highScore` / `maxCombo` | `highScore3` / `maxCombo3` |
| 协议字段 | `progress.endless` | `progress.endless3` |
| 经验除数 | `endlessExpPerScoreDivisor` | `endless3ExpPerScoreDivisor` |
| 反刷分上限 | `maxScorePerMove` | `endless3MaxScorePerMove` |

还有一处隔离：三色爽局的分数**不计入** `games.match3.totalScore` / `stats.totalScore`（服务端按 `isEndless3` 判定的 `countsToTotals`），否则它会靠单局数百万分把累计总分独占。

实现上，标准无尽与三色爽局**共用 `mode-endless.js` 一份渲染流程**，全部差异集中在文件顶部的 `VARIANTS` 表；将来再加同类变体只需往表里加一项。

注：`ENDLESS3.colors = 3` 低于 `COLOR_LIMITS.min`（那是**关卡**校验的下限，避免关卡被设计得太容易连锁），本模式是有意为之，且无尽不走关卡校验，两者不冲突。

### 5.6 肉鸽试炼（娱乐玩法）

**定位：一轮一段 run 的限步冲层。** 与无尽类「单盘长跑」相反，肉鸽每层重建棋盘，强度靠层间祝福累积。

**核心循环**

| 环节 | 规则 |
|---|---|
| 每层开局 | 重新生成 8×8 标准盘，基准 10 步（每 2 层再多 1 步），元素 6 色起 |
| 过关 | 限步内本层得分 ≥ 该层目标分；达标即锁盘，本层不再耗步 |
| 层间 | 从祝福池三选一，祝福在本轮内累计并作用于后续每层 |
| 层内 | 随机给一个「收集某颜色 N 个」的局内任务，达成即当场发放一个**改机制**的奖励（不设失败惩罚） |
| 结束 | 步数耗尽仍未达标即本轮结束；结算「到达层数 + 本轮总分」 |
| 续存 | 一轮 run 会做局内暂存（本地 + 云端，见 5.4 / 8）：刷新、换设备都能接着打当前这一层，包括停在「三选一」时的三个候选与层内任务进度 |

**目标分与步数公式**（`perks.js` 的 `goalOf` / `floorOptions`，config 只给系数）

```
目标分   = baseGoal × goalGrowth^(层数-1) × (1 + perkGoalWeight × (层数-1)) × (1 - goalCut)
本层步数 = movesPerFloor + 祝福加成 + floor((层数-1) / movesPerFloorStep) × (1 + moveGrowth)
得分倍率 = 固定加成累乘 × (1 + floorMult × (层数-1))
颜色权重 = 由「同色磁石」选定的颜色给 magnetMult^叠层，其余颜色为 1（缺省 null = 等概率）
```

**祝福池**（`perks.js` 的 `PERKS`，数据驱动：加一条数据即加一种祝福）

| 祝福 | 效果 | 上限 | 类别 |
|---|---|---|---|
| 🎒 补给包 | 每层起手步数 +2 | 3 | 成长 |
| 🎨 极简主义 | 元素种类 −1（最低 4 色） | 2 | 成长 |
| 💎 熟练手法 | 得分 ×1.25 | 6 | 成长 |
| 🧨 军火库 | 每层开局送 3 个条状 | 3 | 成长 |
| 💣 爆破专家 | 每层开局送 2 个炸弹 | 3 | 成长 |
| 🌈 彩球礼物 | 每层开局送 2 个彩球 | 2 | 成长 |
| 🧭 侦察报告 | 目标分 −18% | 4 | 成长 |
| 🧲 同色磁石 | 随机锁定一种颜色，其出现概率 ×1.7 | 2 | 成长（**改机制**） |
| 🕳 深渊回响 | 每深 1 层，得分倍率额外 +8% | 2 | 成长（层数） |
| 🥾 深入脚步 | 每 2 层多发的步数 +1 | 1 | 成长（层数） |
| 🌪 彩虹风暴 | 每层开局送 3 个彩球 | 2 | 成长 |
| 🎆 火力覆盖 | 每层开局送 3 个条状 + 2 个炸弹 | 2 | 成长 |
| 🔥 血祭 | 本局得分 ×2，代价是每层起手步数 −2 | 1 | 风险（非成长） |
| 🛡 免死金牌 | 步数耗尽时补 3 步继续本层（一次性） | 2 | 工具 |
| 🔄 备用洗牌 | 每层免费洗牌 +1 次 | 3 | 工具 |

前 2 次三选一只出「成长」类（`friendlyPicks`）——模拟标定时观察到开局连出保命/工具牌会直接导致第 2~3 层强度不足翻车。「成长（层数）」类（深渊回响 / 深入脚步）与「血祭」的取舍见下方「层数成长来源」。

**改机制祝福：🧲 同色磁石。** 前面所有祝福都只是「数值变大」，这一张改的是**盘面生成规则**：锁定一种颜色，此后每层开局铺色与连锁补充都按 `colorWeights` 加权（引擎侧为 `cascade.js` 的 `pickColor`），该色占比上升 → 同色更多 → 连锁更长。这是本轮唯一一条**动机制**的祝福，也是「越玩越同色、越同色越炸」的爽感来源。

权重倍率必须卡在**连锁密度突变点之前**。标定实测（10 步中位分）：

| 颜色数 | ×1 | ×1.7 | ×2.9 | ×4 |
|---|---|---|---|---|
| 6 色 | 1755 | 1935 | 2205 | 3080 |
| 4 色 | 6155 | 7670 | 12075 | 20145 |

6 色下权重怎么加都温和，但 4 色下越过 ×3 就非线性起飞（×4 已达 3.3 倍）——因为 4 色时 ×4 权重等于让该色占掉 4/7 的盘面，连锁会自己接起来、接近自动通关。故 `magnetMult` 从 2 收到 **1.7**，叠满（max 2）正好是 ×1.7² = ×2.89，卡在爆发点之前：既是无可争议的强牌，又不至于让盘面「一色独大」到失去操作感。

**局内随机任务**（`perks.js` 的 `questFor` / `QUEST_REWARDS`）

每层（第 2 层起）随机一个「📜 收集 X 色 ×N」，进度取本层累计消除数（棋盘每层重建，`collected` 天然从 0 起算）。**不设失败惩罚**——它的定位是在层内制造一个额外的决策焦点（要不要为了它换一种消法），而不是加难度。达成即当场发放，奖励全部是**当场生效的机制改变**，与层间祝福形成分工：祝福负责「本轮越滚越强」，任务奖励负责「这一层立刻爽一下」。

| 奖励 | 效果 |
|---|---|
| 🥾 补给 | 立即 +5 步 |
| 🔥 狂暴 | 本层剩余步数内得分 ×2（`board.setScoreMult`） |
| 🎆 爆破 | 场上随机 2 颗变成条状（`board.addSpecials`） |
| 🌈 彩球 | 立即获得 1 个彩球 |

目标数 `need = 16 × 1.12^(层数-1)`。模拟里「实际能收到的个数」按约 ×1.11/层上涨，`1.12` 略高于它，于是前期轻松达成、约第 27 层起追不上，16 次 run 的全程达成率落在 **69%**——正好是「想拿就得主动换一种消法」的强度，而不是白送。

**数值标定**（`client-v2/tests/match3-rogue-balance.mjs`，直接 import 产品代码里的公式，改数值前先重跑）

收敛到 `baseGoal 900 / goalGrowth 1.33 / movesPerFloorStep 2 / perkGoalWeight 0.1 / 10 步起 / 6→4 色 / magnetMult 1.7 / need 16×1.12^层`。16 次 run（上限 50 层）实测：**中位第 30 层、p25 第 29 层、最低 16 层、首层 0 次翻车**；局内任务达成率 69%；模拟用的是随机走子，真人水平会更高几层。整轮总分中位约 **4709 万**（旧版 80 万，×59），终局倍率约 **×45**，因此反刷分的单步上限同步上调（见 9.4），经验也一并改为**按到达层数**换算、不再跟着分数走（见 5.7 / 9.5）。

**关键设计：层数成长来源。** 棋盘参数（颜色数 / 得分倍率 / 特殊元素）只由祝福决定，祝福叠满后每层的「可达分平台」就固定了。若没有随层数增长的来源，目标分的指数曲线迟早越过这条平台，run 必然在固定层数猝死、且后期分数横盘——这正是实测反馈「buff 不够强力、后面分数上不去」的根因。解法是引入两条**随层数增长的轴**，且都只由「深渊回响 / 深入脚步」两张祝福激活（不加这两张牌时 `floorMult = moveGrowth = 0`，行为与旧版完全一致）：

1. **步数轴**：每 `movesPerFloorStep` 层多发 `(1 + moveGrowth)` 步，让「每层能下多少步」随深度上涨；
2. **倍率轴**：得分倍率再乘 `(1 + floorMult × (层数-1))`，线性上涨，让每层分数不是「持平」而是「越滚越大」。

加上「同色磁石」这条**机制轴**，三条轴的合力与目标分的指数曲线在 **30 层上下交汇**，即为 run 的自然终点：期望反馈是「越往后每一步的分越大、终局能看到 ×45 的倍率」，而不是旧版叠满祝福后从第 10 层起可达分稳定在 2 万、到第 15 层就打不动。相应地，`goalGrowth` 从 1.28 抬到 **1.33**：1.28 配合这两条轴会把 run 拖到 33 层、整轮总分 3860 万（尺度失控），1.38 又太陡（中位掉到 18 层、最低 6 层翻车），1.33 才落在「中位 30 层 + 不出现大批翻车」的区间。

标定过程中被否掉的几版：

- `baseGoal 1500` 太贴 6 色 10 步的中位分（1750），「脸黑停在第 2~3 层」的 run 大量出现；
- `goalGrowth 1.15 / 1.19 / 1.22` 配层数成长后过松（中位 25~29 层，全部打满模拟上限），说明目标曲线被削得太狠；
- 「连锁倍率上限」祝福实测在 6 色 / 4 色下**完全无效**（上限 5/7/9/11 的中位分都是 1755 / 7130），只保留引擎参数、不进祝福池；
- 「深渊回响」上限 3（+24%/层）配 `goalGrowth 1.28` 会把 run 推到 34 层、整轮 5880 万，深层单步得分反而越过反刷分线，故收紧到上限 2；
- 「同色磁石」`magnetMult 2`（叠满 ×4）在 4 色下把整轮总分从 1685 万顶到 1.1 亿、均步得分逼到反刷分线（余量只剩 1.2 倍），故收到 1.7；
- 局内任务 `needGrowth 1.09` 太浅（达成率 88%，等于每层白送一个奖励），抬到 1.12 后落到 69%。

**硬约束：元素种类下限 4 色**（`ROGUE.minColors`）。3 色每步均分 66,187 比 4 色的 5,295 高约 10 倍，若允许降到 3 色，「极简主义」会变成压倒性最优解且分数尺度失控——3 色留给无尽三色。

**成绩隔离**（沿用 5.5 的三层思路，`mode='rogue'`）

| 层 | 字段 |
|---|---|
| 客户端存档键 | `match3BestRogue`（`{ maxFloor, highScore }`） |
| 账号字段 | `rogueMaxFloor` / `rogueHighScore` |
| 协议字段 | `progress.rogue` |
| 经验公式 | 按到达层数：`⌊层数² × rogueExpFloorFactor（1.16）⌋ × 局外「经验共鸣」`（**不按分数**，见 5.7 / 9.5） |
| 反刷分上限 | `rogueMaxScorePerMove`（300,000/步，等同不设限，见 9.4）；另加「层数 ≤ 步数」与 `maxFloor` 两道层数上限（精华与经验都按层数给，必须挡住层数虚报） |

与 5.5 一致，肉鸽的分数**不计入** `games.match3.totalScore` / `stats.totalScore`，`maxCombo` 也不并进共享的无尽最高连锁（`countsToTotals` / `maxCombo` 均按 `isRogue` 判定）。

**实现落点**：`mode-rogue.js` 只做状态机与渲染，数值与推导全在 `perks.js` / `config.js`（`ROGUE`）；祝福与任务奖励的**总览**在 `codex.js`（`showPerkCodex`，内容直接由 `PERKS` / `QUEST_REWARDS` 生成，加祝福不用改它）；board 侧为肉鸽新增了四个开局参数：`scoreMult`（得分倍率）、`cascadeMax`（连锁倍率上限）、`specials`（开局注入特殊元素）、`colorWeights`（颜色出现权重），以及 `addMoves` / `shuffle` / `setScoreMult` / `addSpecials` 四个方法（后两个供局内任务奖励在层中改机制）。

**数值可见性**：`mode-rogue.js` 的 `bonusStats(bonus, floor)` 把加成折算成该层实际生效的数值（口径复用 `floorOptions` / `goalOf`，不另立一套），对局中（左栏）与结算后（终局参数）都展示；三选一时改由每张卡片用 `perkDelta` 列出「本层 → 下一层」的原值 → 新值，玩家对着背景里保留的盘面就能看出每个祝福的收益，不必再把整页换成一张对照表。**对局中这些数全部收进左侧侧栏**（本层进度含达标进度条 / 本轮加成 / 已获祝福带叠加层数），棋盘上方只留整轮累计读数——横排在正上方时挤成一行小标签，既放不下「得分与目标」的关系也看不出祝福叠了几层（详见七、UI 结构）。局内任务条在侧栏内、进行中显示「📜 收集 色×N · 进度 N/M · → 奖励」，达成后整条转为「✅ 奖励名 + 效果说明」，同时弹一条 toast。

### 5.7 肉鸽局外养成（精华 / 局外增益 / 祝福解锁与升级）

**闭环**：打一局 run → 按到达层数拿「精华 ✦」→ 在图鉴里花掉（解锁新祝福进三选一池 / 升级已有祝福提升单次效果 / 解锁升级局外增益 / 领收集里程碑奖励）→ 下一轮更强、能打得更深 → 拿更多精华。所有环节都落在同一份存档里，路径单一。

**只发精华，不发道具券。** 对局道具（提示、悔棋那套）与肉鸽养成是两套经济，混在一起会让「打 run 兑换道具」变成绕开道具定价的旁路。里程碑奖励同样只给精华。

**两层 buff：局内祝福 vs 局外增益**

同一套精华买两种东西，区别只在作用范围：

| | 局内祝福（`PERKS`） | 局外增益（`META_BUFFS`） |
|---|---|---|
| 作用范围 | 仅本轮 run，改每层开局参数 | 跨轮常驻，改每层开局参数或直接作用于结算 |
| 获取方式 | 每层三选一抽一张 | 只能花精华解锁 / 升级，且要沿**共鸣树**的前置逐级买（见下） |
| 一轮结束 | 全部清空 | 保留，永久生效 |
| 进三选一池 | 是（未解锁的不出现） | 否（买了就一直在） |
| 存档字段 | `rogue.perks` | `rogue.buffs` |
| 节点类型 | 只有数值类 | 数值节点（`kind: 'value'`）+ 机制节点（`kind: 'mechanic'`） |

唯一标记是 `scope: 'buff'`（`perks.js`）：`meta.js` / `codex.js` 靠它决定「这项几级了」去 `perks` 还是 `buffs` 里读，其余（稀有度档、费用表、等级曲线、升级事件）两层完全共用。**局外增益未解锁按 ×1 计，不是按 lv1**——它是纯增益，没买就没有，故 `buffFactor` 单独处理这一点，不能直接拿 `valueAt(buff, 0)`。

**局外增益按「共鸣树」组织**（`perks.js` 的 `META_BUFFS`，共 **9 节点 = 6 数值 + 3 机制**）

参考图（《崩坏：星穹铁道》的「货币战争 · 优势布局」）里那种**带连线的天赋树**：中央一颗根节点「精华 ✦」向下分叉成 3 条流派，每条流派 2 个数值节点 → 末端 1 个机制节点。三条流派各给一个方向上的成长，玩家沿自己那条线往下买：

| 流派 | 数值节点（小颗 · 可逐级升级） | 机制节点（大颗 · 一次性解锁） |
|---|---|---|
| 经济流（第 0 列） | 📘 经验共鸣（epic，×1.2 + 0.15/级）→ 🔷 精华共鸣（rare，×1.1 + 0.1/级） | 💰 丰收闭环（epic） |
| 开局流（第 1 列） | 🎒 起始补给（common，每层起手步数 +1/级）→ 🌈 开箱彩球（rare，每层开局附赠 1 彩球/级） | 🎁 先手规划（epic） |
| 保命流（第 2 列） | 🛡 常驻护盾（common，每轮免死 +1/级）→ 🔄 常驻洗牌（common，每层免费洗牌 +1/级） | ⏳ 时光倒流（epic） |

**与参考图刻意的两处不同**：

1. **不做「已布局 N/M」的布局上限**。参考图有 `已布局优势 40/40`（换搭配要洗点），本作是长期养成，上限只会让人不敢买——**点亮即生效**，精华花了就永久生效，没有任何拆卸与重置流程。
2. **树只承载局外增益**，局内祝福仍按稀有度平铺在共鸣树下方（见「图鉴即养成面板」）。局内祝福是每轮三选一抽的消耗品，放进树里只会让「这轮抽到哪张」与「树点亮了哪颗」两件事互相干扰。

**数值节点 vs 机制节点**（唯一区分是 `kind`）

- **数值节点**沿用既有的一整套：`scales` 曲线 + `ROGUE_META.rarities` 的等级上限 / 费用，可逐级升级，每级都更强（`maxLevelOf` 走稀有度）。
- **机制节点**是**真正改规则**的新效果，不是现有祝福的弱化常驻版：一次性解锁、**上限固定 Lv.1**（`maxLevelOf` 对它直接返回 1）、费用只由稀有度决定；没有 `scales`，`desc` 是一句静态说明。

| 机制节点 | 改的规则 | 参数（`ROGUE_META.mechanics`） |
|---|---|---|
| 💰 丰收闭环 | 图鉴里程碑奖励 ×2；每轮结算额外拿一笔按层数的定额精华 | `milestoneMult 2` / `essencePerFloor 2` |
| 🎁 先手规划 | 每轮**第 1 层**起手步数 ×2；第 1 层过关后三选一**连抽 2 次**（多拿一张祝福） | `firstFloorMovesMult 2` / `firstFloorPicks 2` |
| ⏳ 时光倒流 | 每轮 1 次：本层步数耗尽仍未达标时**重置该层重打**，不判本轮结束 | `retriesPerRun 1` |

三个都刻意只作用于「开局 / 结算」这类**边界**，不碰局内计分规则：丰收闭环只加精华（不碰经验），先手规划的步数倍率**只放大第 1 层**（后面几层按原曲线走，否则等于白送一整条步数成长轴），时光倒流只给一次机会且不可升级（它是唯一能往上抬层数的机制，见「标定结论」）。

**前置关系就是连线**（`requires: [前置 id]`）。第一颗数值节点没有前置（连到根节点），第二颗的前置是第一颗，机制节点的前置是第二颗。客户端按 `requires` 画连线、前置没点亮时置灰（`requiresMet`），服务端 `upgradeRoguePerk` 也会拒绝——两端同一套判定，改不了本地存档硬买。

**坐标随数据走**（`tree: { col, row }`）：`codex.js` 用它定位落格（CSS grid 的 `grid-column` = `col + 1`、`grid-row` = `row + 3`，前两行留给根节点与分叉线）。**加一颗节点只改 `perks.js` 一处**，渲染与连线不用动。

**精华与经验都按「到达层数」结算，不看分数**

```
本轮精华 = ⌊ 到达层数² ÷ 5 ⌋ × 精华共鸣  +  丰收闭环定额 ⌊到达层数 × 2⌋     （第 10 层 20 · 第 30 层 180，丰收闭环再 +60）
本轮经验 = 基础经验 + ⌊ 到达层数² × 1.16⌋ × 经验共鸣
```

理由与 5.6 的「层数成长轴」直接相关：后期得分倍率能堆到 ×45，同一层数的分差可以差几个量级（标定 5.7 实测：全满级玩家的整轮总分是未养成的 **72 倍**）。按分结算会让「堆分」的收益压过「打深」，而堆分恰恰是后期自动发生的事，等于白送。层数最直观、也最好控，且平方曲线天然形成「越深收益越高 → 值得为打深投资祝福」的正循环。**经验同口径**——见 9.5，它原先按整轮总分 ÷ 45000 换算，会给满级玩家白送约 ×73 的经验（详见「标定结论」）。

两道层数上限兜底：`maxFloor`（100，正常打不到，标定上限 50 层、实测最深 44 层）截断，服务端与客户端同源；服务端另加「层数 ≤ 已用步数」（见 9.4），防「层数报个大数」把精华与经验一起套走。`essenceDivisor`（5）与 `maxFloor` 都随 `match3_progress.rogue.cfg` 下发，改服务端一处即生效。

**等级上限与费用按稀有度分组（一键调平衡）**

祝福与局外增益都只在 `perks.js` 里声明自己属于哪一档，其余全从 `ROGUE_META.rarities` 查表（两层共用同一张表，新增增益不用再造一份费用口径）：

| 稀有度 | 局内祝福 | 局外增益（数值节点） | 局外增益（机制节点） | 等级上限 | 解锁费 | 升级费（lv1→lv2） | 每级费用递增 |
|---|---|---|---|---|---|---|---|
| 普通 common | 补给包 / 极简主义 / 军火库 / 爆破专家 / 侦察报告 / 免死金牌 / 备用洗牌 | 🎒 起始补给 / 🛡 常驻护盾 / 🔄 常驻洗牌 | — | 2 | 20 | 25 | ×1.5 |
| 稀有 rare | 熟练手法 / 彩球礼物 / 深入脚步 | 🔷 精华共鸣 / 🌈 开箱彩球 | — | 3 | 50 | 70 | ×1.5 |
| 史诗 epic | 同色磁石 / 深渊回响 / 彩虹风暴 / 火力覆盖 / 血祭 | 📘 经验共鸣 | 💰 丰收闭环 / 🎁 先手规划 / ⏳ 时光倒流 | 4（机制节点固定 1） | 100 | 150 | ×1.5 |

`upgradeCost × costGrowth^(lv−1)` 让费用随等级上涨，避免精华全砸在一张牌上。将来加高上限或整体调价，改这张表一处即可，不用逐条祝福改数字。**机制节点只借这张表的 `unlockCost`**（都是 epic，解锁 100 精华），上限与升级费对它没有意义——`maxLevelOf` 直接返回 1，`nextStep` 到 Lv.1 就是 `null`（按钮变「已点亮」）。

**等级 → 效果曲线（`scales`）**

```
add ： valueAt = base + per × (lv − 1)          —— 加量类（步数 / 个数 / 档数）
mult： valueAt = base × (1 + per × (lv − 1))    —— 比例类（得分倍率 / 目标减免 / 权重）
```

`scales.base` 就是 **lv1 的数值**，即 v1.16 及以前写死的那些数字——**未升级时与旧版逐位一致**，所以这次改动不会动到既有的 30 层基线。祝福的 `desc` 同步改成 `desc(lv)` 函数（按等级生成文案），`apply(bonus, ctx)` 的签名由 `ctx = rng` 改为 `ctx = { lv, rng }`：`lv` 决定这次累加多大（缺省 1），`rng` 仍供「同色磁石」锁色（三选一卡片上的预览不传 rng，故预览显示「随机一色」）。**机制节点没有 `scales`**，`valueAt` 对它求值会得到 `NaN`，所以凡是要算「这条满级是多少」的地方（图鉴、标定脚本）都必须先按 `kind` 分流。

**解锁决定池子**：`rollPerks(rng, picks, allowed)` 的第三个参数是已解锁 id 集合，未解锁的祝福不会出现在三选一里。于是「集齐祝福」是**有实际收益**的目标，而不只是图鉴里的一个数字。新号初始解锁三张（补给包 / 极简主义 / 熟练手法，刻意都属成长类，保证开局三选一有牌可选）。

**服务端权威，本地只做临时缓存**

| 环节 | 权威方 | 说明 |
|---|---|---|
| 数值表（上限 / 费用 / 里程碑） | 服务端 | 随 `match3_progress.rogue.cfg` 下发，客户端 `ROGUE_META` 只在离线 / 游客时兜底，避免「界面按旧价显示、点下去被服务端拒绝」 |
| 精华余额 / 祝福与增益等级 / 里程碑领取 | 服务端 | 解锁升级只上报 `perkId`（祝福与增益同一个 id 空间）、领奖只上报 `milestoneId`，价格、上限、扣费、达成条件全在服务端锁内现算 |
| 结算倍率 / 机制结算 | 服务端 | `rogueBuffMult(rogue, buffId)` 是唯一倍率计算点，与客户端 `valueAt` 同口径（两位小数）；「丰收闭环」的里程碑翻倍与定额精华、机制节点的生效判定（`_rogueMechanicOn`）同样只在服务端结算；经验 / 精华的最终值只在服务端算，客户端那套只用于预览 |
| 存档展示 | 客户端 | `localStorage` 里那份是**临时缓存**，只为离线看图鉴与局内抽牌，一联网就被 `match3_progress` 覆盖 |

落点：`AccountManager` 的 `_normalizeRogue` / `getMatch3Rogue` / `_patchMatch3Rogue` / `addRogueEssence` / `upgradeRoguePerk` / `claimRogueMilestone` / `_rogueMilestoneState` / `rogueBuffMult` / `_rogueBuffMaxLevel` / `_rogueMechanicOn`；socket 事件 `match3_rogue_upgrade`（**同一个事件处理祝福与增益**，回执带 `scope` 区分）/ `match3_rogue_claim`（回执 `match3_rogue_meta`，带最新存档，客户端据此重画）；计算与推导在客户端 `rogue/meta.js`（`rarityOf` / `maxLevelOf` / `costToUpgrade` / `nextStep` / `itemLevel` / `buffFactor` / `essenceForRun` / `poolProgress` / `milestoneState`，以及共鸣树用的 `mechanicCfg` / `mechanicOn` / `requiresMet` / `applyMetaBuffs` / `milestoneReward`），标定脚本复用同一份公式。养成存档与逐关星表、局内暂存在**同一个文件** `data/match3/<accountId>.json`，故必须经 `_patchMatch3Store` 在锁内合并，绝不整文件覆盖写。

**服务端为共鸣树补的三处**（`server/config.js` 与 `client-v2/src/games/match3/rogue/perks.js` 是**两份手工同步的配置**，改树要一起改，否则「界面能买、服务端拒绝」）：

1. `match3Rogue.buffs` 由 2 项扩到 9 项，每项补 `kind` / `requires`（只有经验 / 精华共鸣需要登记 `base` / `per` 用于结算倍率，其余只为校验上限与前置）；
2. 新增 `match3Rogue.mechanics`（三个机制节点的参数表，与客户端 `ROGUE_META.mechanics` 同源同值）；
3. `upgradeRoguePerk` 加**前置校验**（`requires` 里任一节点未点亮即拒绝），`_normalizeRogue` 改按 `_rogueBuffMaxLevel` 裁剪等级（机制节点裁到 1）。

**存档记录得全**（当前界面用不到，但给后续功能留数据）

- 每条祝福：`lv` / `unlockedAt`（0 = 开局赠送，与花钱解锁区分）/ `upgradedAt` / `picks`（累计被选次数）
- 每条局外增益：`lv` / `unlockedAt` / `upgradedAt`（没有 `picks`——它不进三选一，永远抽取不到）；机制节点与数值节点**共用同一张 `buffs` 表**，区别只在 `lv` 恒为 1（机制节点没有更高的级，`lv ≥ 1` 即「已点亮」）
- 汇总 `stats`：`runs` / `bestFloor` / `totalCleared` / `questsDone` / `picked`（累计拿过的张数）/ `spent`（累计花销）/ `firstRunAt` / `lastRunAt`
- `essenceEarned`（累计获得，与余额分开）；`claimed` 只保留配置里仍存在的里程碑 id

**里程碑**（一次性领取，奖励只有精华）

| id | 条件 | 奖励 |
|---|---|---|
| `unlock3` / `unlock6` / `unlock10` | 解锁 3 / 6 / 10 种祝福 | 20 / 40 / 80 |
| `unlockAll` | 集齐全部 15 种 | 200 |
| `maxAny` / `max3` | 任意 1 张 / 3 张升到满级 | 30 / 120 |

达成条件由服务端按存档独立算一遍（`_rogueMilestoneState`），不采信客户端上报。**点亮「丰收闭环」后这张表的奖励统一 ×2**（`milestoneReward` 与 `claimRogueMilestone` 同口径），图鉴里也按翻倍后的数展示——否则玩家会以为点了没生效。

**图鉴即养成面板**（`rogue/codex.js`，仍是 `showPerkCodex`）

顶部是精华余额、收集度（已解锁 N/15 · 已满级 M）、**当前局外增益倍率**（`📘 ×1.74 · 🔷 ×1.32`，未解锁显示 ×1）、累计获得 / 花费 / 出战轮数 / 最深层；下面依次是里程碑（达成待领会点亮，奖励按丰收闭环翻倍显示）、**「✦ 共鸣树 · 已点亮 on/9」**（树本体 + 选中节点详情卡）、按稀有度分组的局内祝福（每条：稀有度标签 / `Lv.x/y` 等级条 / 当前效果 / 下一级效果 / 按钮，行末标注「本轮上限 N 张」）、局内任务奖励。三个入口共用：娱乐菜单（含养成状态行）、对局左栏（「✦ 精华」块的「养成」与「已获祝福」块的「图鉴」）、三选一模态框底部。面板外框仍是 `components/modal`，借 `.modal-overlay--codex` 把 `max-width` 从 420px 放宽到 560px。

**共鸣树的画法**（`treeSection` / `treeNode`，全数据驱动）

用 CSS grid 落格 + 绝对定位的小条画连线，**不引 SVG**：

- 3 列网格，根节点（`.m3-tree-rootcell`）横跨整行；下面一行是分叉线（一根横贯穿线 `.m3-tree-fan-bar` + 每列一根向下的小竖线 `.m3-tree-fan-stub`）；
- 每颗节点是一个 `grid-column = tree.col + 1` / `grid-row = tree.row + 3` 的格子，格子里的按钮按状态上色：`--on`（已点亮，稀有度色顶边）/ `--next`（买得起，可点）/ `--blocked`（前置没点亮，置灰 + 标「需先解锁 XX」）/ `--mechanic`（大颗机制节点）/ `--sel`（当前选中，高亮描边）；
- 连线是上一颗节点格子底部的 `.m3-tree-link`，靠格子自身的相对定位对齐——**行高变化不会让线飘走**（这是不用 SVG 的理由）；
- 点节点只是 `selectedId = id` 然后重画，详情卡复用原有的 `perkRow`（含 `Lv.x/y` 等级条 / 当前效果 / 下一级花费 / 按钮），**树的浏览与购买是同一个组件**；
- 打开面板时的默认选中项（`defaultSelection`）优先挑「前置已满足且未满级」的节点，玩家一进来就有一件能买的事。

局外增益与局内祝福在代码里走同一套渲染（`perkRow` 按 `scope` 分支换标题与行末标注，按 `kind` 分支换「机制」标签与等级条），加一条增益只多一行数据、加一颗节点只多一行 `META_BUFFS`。

**机制节点在局内怎么落地**（`mode-rogue.js`）

两个改局内的机制（丰收闭环只改结算，落点在 `addRogueEssence` / `claimRogueMilestone`）：

- **🎁 先手规划**：`startRun` 时读 `mechanicOn(meta, 'planning')` 写进 bonus 的 `firstFloorMult`，`floorOptions` 在**第 1 层**才乘上去；第 1 层过关后置 `extraPicks = firstFloorPicks - 1`，`choosePerk` 里每多抽一张就减 1（期间 `floor` 不推进），三选一模态框的副标题会写「🎁 先手规划：本层还能连选 N 张」。
- **⏳ 时光倒流**：`rewindsLeft` 在 `startRun` 时按 `retriesPerRun` 初始化、随暂存一起存（`toSession` / `resumeRun`，刷新页面不吞次数）；`onGameOver` 里排在**免死之后、判本轮结束之前**——还有次数就把本层重打一遍。重建用 `setTimeout(…, 0)` 而非就地调 `mountFloor()`：`onGameOver` 是从 board 内部回调出来的，就地重建会在棋盘还在执行时把它拆掉；期间用 `rewinding` 标志挡住重复触发的结束判定。侧栏「本轮加成」里会多一行「⏳ 时光倒流 ×N」，让玩家看得见还剩几次。

| 全满级（祝福满级） | 39 | 34.6 亿 | +304 | +1764 |
| 树 + 祝福全满 | 38 | 34.8 亿 | +288 | +1675 |

「精华基础 / 经验基础」是**未乘局外倍率的原始数**（`⌊层数²/5⌋` 与 `⌊层数²×1.16⌋`）。乘上「精华共鸣 ×1.32 / 经验共鸣 ×1.74」、精华再叠加丰收闭环的 `⌊层数×2⌋` 之后，「树 + 祝福全满」一档实际到手是：精华 `288×1.32 + ⌊38×2⌋ = 380 + 76 = 456`、经验 `1675×1.74 = 2914`。

层数 +9（+30%）即养成的总回报，量级可控；总分 ×72 是深层倍率叠加的结果——**这也是精华与经验都必须按层数而非按分结算的直接证据**（按分结算会把这 ×72 原样送成账号等级）。

**共鸣树只贡献 +1 层**（30 → 31，总分 +69%）——树是**长期养成的起点**而不是强度大头：它的价值主要在经济侧（经验 / 精华倍率、里程碑翻倍），局内那两颗只影响第 1 层与容错。**重点看的是「不失控」**：⏳ 时光倒流每轮只多一条命、🎁 先手规划只放大第 1 层步数，两者都是不可升级的一次性机制，所以「全点亮」不会把层数抬飞（树 + 祝福全满 38 层，与只有祝福全满的 39 层同档，差异是 16 次 run 的噪声）。这也是机制节点刻意不做可升级的理由。

**经验尺度**：按层数结算后，全满级也只是 `1044 → 1764`（层数 30→39 的平方，1.69 倍）；再乘上局外增益「经验共鸣」满级 ×1.74，合计约 **2.94 倍**。相较旧版按总分 ÷45000 的约 ×73（1044 → 76900），已压到个位数——经验的「打深复利」被拆成两层：层数只给平方增长，剩下的倍率交给玩家自己花精华买、且封顶 ×1.74。

**精华同理**：只因「精华共鸣 ×1.32」与丰收闭环的定额涨一档（180 → 456），两条曲线都封顶，不会随局数继续膨胀。

脚本的一致性检查同步扩到三类：① 每条祝福与局外增益声明的稀有度都必须在 `ROGUE_META.rarities` 里存在（否则界面会静默退回 common 档，数值对不上却查不出原因）；② 全部 id 唯一（祝福与增益同一个 id 空间，重名会让升级事件写错表）；③ **共鸣树结构**（`assertTreeCovered`）——坐标不重复、`requires` 指向的节点存在且同列且确实在上一层、机制节点没有 `scales` 且必带前置、每条流派恰好收在一个机制节点上。树是数据驱动的，写错一个字界面只会画歪或静默少一条线，所以这三类都在标定时一次性拦下。

### 6.2 设计要点

| 项 | 方案 |
|---|---|
| 引擎与渲染分离 | `grid` / `match` / `special` / `cascade` / `deadlock` 均为纯逻辑，不碰 DOM，可在控制台或 Node 中独立跑用例验证 |

| 动画编排 | `async/await` 串 Promise：交换 150ms → 消除 200ms → 下落 250ms → 补充 → 下一轮连锁；动画期间锁输入 |
| 棋盘生成 | `initial` 为空时按 `colors` 随机生成，并强制保证「无现成三连」+「至少一个可行交换」；配套开发期关卡校验脚本（见风险清单） |
| 状态管理 | 对局状态放模块内局部 state（对齐贪吃蛇的做法）；只有跨页面数据（关卡进度、最高分）走 `store` + `api` |
| 主题适配 | 所有颜色走 CSS 变量，自动跟随现有主题切换 |

### 6.4 配置化原则

**所有数值、开关、阈值一律不写死在逻辑里。** 按归属分三层：

| 层 | 位置 | 放什么 | 例子 |
|---|---|---|---|
| 游戏配置 | `client-v2/src/games/match3/config/config.js` | 全局玩法参数与表现参数 | 棋盘尺寸上下限、元素种类上下限、各类消除分值、连锁倍率曲线、无尽难度分档表、动画时长 |
| 关卡配置 | `client-v2/src/games/match3/config/levels.js` | 与单关相关的数值 | 棋盘尺寸、mask、元素种类、步数、目标、障碍、星级阈值 |
| 服务端配置 | `server/config.js` 的 `match3Rewards` | 奖励与风控 | 经验公式参数、反刷分阈值 |

硬性要求：

- 逻辑代码里**不出现魔法数字**——`0.5`（倍率步长）、`150`（动画时长）、`50000`（难度分档门槛）这类必须命名并抽到配置
- 无尽模式的难度分档、连锁倍率曲线**必须是数据表**，不是 if-else 链；将来调平衡只改数据、不改逻辑
- 动画时长、连击反馈等表现参数同样进配置，便于统一调整手感
- 配置项命名自解释，改配置不需要读逻辑代码

一句话：**逻辑只负责"怎么算"，配置负责"算多少"。**

### 6.5 引擎的单元验证方式

引擎层全部是纯逻辑、不碰 DOM，因此用 Node 直接跑用例验证，不依赖浏览器。项目根 `package.json` 是 CommonJS（服务端用 `require`），无法直接 `import` 客户端的 `.js`，需在 `client-v2/` 下放一个 `package.json` 标记该子树为 ESM：

```json
{ "type": "module" }
```

该文件只影响 Node 的模块解析，浏览器始终按 `<script type="module">` 处理，对运行时零影响。用例放在 `client-v2/tests/`，通过 `node client-v2/tests/match3-engine.test.js` 执行。

`Lv.x/y` 等级条 / 当前效果 / 下一级花费 / 按钮（机制节点没有等级条，按钮到 Lv.1 就变「已点亮」）。

标题右侧的「图鉴」、三选一模态框底部的「📖 图鉴」。从三选一里打开时面板盖在它上面

## 八、存档结构

本地键（写在本机）+ 云端字段（同一账号跨设备）：

| 键 | 内容 | 说明 |
|---|---|---|
| `match3Progress` | `{ maxLevel, stars: { 关号: 星数 } }` | **闯关进度以服务端为唯一真相**，本地只是服务端进度的缓存 |
| `match3Best` | `{ highScore, bestCombo }` | 标准无尽，本地与服务端取 max 合并 |
| `match3Session` | 局内暂存，见下 | 标准无尽，刷新 / 换设备后续玩 |
| `match3BestEndless3` | `{ highScore, bestCombo }` | 无尽三色，与 `match3Best` 完全隔离（见 5.5） |
| `match3SessionEndless3` | 同 `match3Session` 结构 | 无尽三色局内暂存 |
| `match3BestRogue` | `{ maxFloor, highScore }` | 肉鸽试炼，与其它模式完全隔离（见 5.6） |
| `match3SessionRogue` | 肉鸽一轮的暂存 | 见下：本轮 run 的层数 / 祝福 / 棋盘 / 任务 / 随机数状态 |
| `match3RogueMeta` | `{ version, essence, essenceEarned, perks, claimed, stats }` | 肉鸽局外养成的**临时缓存**（见 5.7）：只为离线看图鉴与局内抽牌，**服务端权威**，一联网就被 `match3_progress.rogue.meta` 覆盖 |

局内暂存（`*Session*`）与上面那些「历史最佳」的性质不同，是**一份未结算的当前进度**，三条规则：

1. **三档并存**：`endless` / `endless3` / `rogue` 各占一个键，同一玩法只留最新一份（`{ mode, ..., ts }`，`ts` 用于比新旧）。
2. **云同步**：本地每次变化覆盖写，云端按 15s 节流推一份（`match3_save_session`），并随 `match3_sync_progress` 的 `sessions` 下发（落 `data/match3/<accountId>.json` 的 `sessions`）。合并**不取 max**，只认 `ts` 更新的那份。
3. **结束写墓碑**：结算时写 `{ mode, finished: true, ts }` 占住同一个键并推上云端。它既不会被当成可续玩的局，又能把别的设备上那份旧暂存压掉——机制细节见 5.4。

肉鸽的暂存内容与其它两档不同：它存的是一轮 run（`phase`、`floor`、`picks` 祝福计数、`bonus` 加成、`quest` 任务进度、`runRngState` 随机数内部状态、`board` 快照），恢复时不重掷祝福候选与任务，随机序列接着上次走。`phase = perk`（停在三选一）时**同样存盘面**——三选一是盖在盘面上的模态框，续玩时背后要摆出刚达标那一层；恢复顺序是「先 `mountFloor` 摆盘面并 `lock`，再挂模态框」，反过来模态框会被 `mountFloor` 的 `replaceChildren` 冲掉。棋盘快照另含 `scoreMult`——肉鸽的局内任务「狂暴」会在层中抬这个倍率，不写进快照刷新后就还原不回来。

冲突处理原则：**只有展示用的最佳分取 max 合并**；闯关进度（解锁与星数）完全由服务端下发覆盖本地，
本地不作为进度来源。原因是进度一旦本地领先，9.4 的「关卡推进」校验会一直判跳关，
而 max 合并又让本地永远领先——玩家自此拿不到经验、也进不了闯关榜，无法自愈。
代价是未登录 / 断线时打的通关不计进度（界面上会提示），且换设备后只能继续服务端已记录到的关卡。

```js
{

  rogueMaxFloor: 0,    // 肉鸽试炼最深到达层数（与其它模式隔离，见 5.6）

{ totalGames, totalScore, highScore, maxLevel, totalStars }

// data/match3/<accountId>.json —— 逐关明细、局内暂存与肉鸽养成共用一个 per-user 文件
{ userId, stars: { 关号: 星数 }, sessions: { endless?, endless3?, rogue? },

    version: 1,
    essence: 0, essenceEarned: 0,            // 余额 / 累计获得（分开：余额会花掉，累计不会）

      [perkId]: { lv, unlockedAt, upgradedAt, picks }   // unlockedAt = 0 表示开局赠送，与花钱解锁区分
    },
    buffs: {                                 // 局外增益 = 共鸣树（跨轮常驻，见 5.7）：同样只存已解锁的；没有 picks（不进三选一）

    },
    claimed: { [milestoneId]: 领取时间戳 },   // 只保留配置里仍存在的里程碑 id

```

**注意**：结构里**不包含** `wins` / `losses` / `draws`（与 `games.snake` 一致）。

**为什么逐关星表要单独存**：星表是唯一随关卡数线性增长的字段（30 关约 0.5 KB，1000 关就是十几 KB），
而账号文件是整体读写的——`dataStore.writeOne` 每次都用 `JSON.stringify(整个记录)` 重写文件，
登录、加经验、发邮件、聊天任何一次账号写入都会把星表一起序列化重写一遍。
拆成独立集合（与 `inventories` / `mails` 同一套 `splitByIdCollections` 机制）后，
随关卡增长的部分不再进账号文件，排行榜、成就、跳关校验读的都是账号里的汇总标量，零改动。
老账号里残留的 `games.match3.stars` 由 `AccountManager.getMatch3Stars` 在首次读取时
按关取最高合并到独立文件、并从账号中删除（惰性迁移，无需启动时全量扫描）。

### 9.4 反刷分校验

在 `match3_game_end` 内执行，任一不通过则：记日志 → 不发经验 → 不入榜。

| 校验 | 规则 |
|---|---|
| 分数与步数 | `score ≤ moves × 本模式单步上限`（闯关 / 标准无尽 25000；无尽三色 60000；肉鸽试炼 300000） |
| 分数与时长 | `durationMs ≥ moves × minMsPerMove` |
| 关卡推进 | `mode === 'level'` 时 `level ≤ maxLevel + 1`（防跳关） |
| 层数与步数 | `mode === 'rogue'` 时 `floor ≤ moves`（每层至少走 1 步才能过关，故层数不可能多于总步数） |

`maxScorePerMove` 按「客户端缩放后的单步有效分」定：实测极值为 4色 8948 / 5色 12498 / 6色 5148 / 7色 4961 / 8色 5871，取 25000 留约 2 倍余量，避免正常长连锁被误杀。**改 `COLOR_SCORE_MULTIPLIER` 后必须回来看这一项**（倍率抬一倍，此项也要跟着抬，否则正常玩家会被判违规）。

`endless3MaxScorePerMove` 单独放宽到 60000：三色爽局不分档、不缩放，连锁极长，实测人类水平每步均分约 16,600、单步最高约 15 万，沿用 25000 会把正常玩家误判为刷分（见 5.5）。

`rogueMaxScorePerMove` 取 300000，对正常玩家**等同不设限**：肉鸽有「深渊回响」这条层数成长轴（每深 1 层倍率再乘一档）与「同色磁石」这条机制轴（某色出现概率 ×1.7，叠满 ×2.89），深层单步得分会被推到 10 万级，且它本身是娱乐玩法、不值得为反刷分牺牲手感。模拟 16 次 run 的整轮均步得分最高 77,969，真人水平更高，取 300000 留约 3.8 倍余量；这一项只兜底拦住明显伪造的上报，不作为强度平衡手段（见 5.6 的层数成长来源）。

`floor ≤ moves` 这条单独加，是因为**精华与经验都按到达层数给**（见 5.7），层数已成了直接换钱的字段：只挡分数挡不住「分数照旧、层数报大」。层数每层至少要走 1 步才可能过关，故上限就是总步数；`maxFloor`（100）再兜一层。两道都拦下才放行结算。

### 9.5 经验公式

在 `server/config.js` 新增（对齐现有 `config.snakeRewards` 的写法）：

```js
match3Rewards: {
  baseExp,
  expPerScoreDivisor,          // 闯关模式经验换算除数
  endlessExpPerScoreDivisor,   // 标准无尽经验换算除数（无尽一局得分可达数万分，须用更小的除数）
  endless3ExpPerScoreDivisor,  // 无尽三色经验换算除数（一局可达数百万分，是标准无尽的约 20 倍尺度）
  rogueExpFloorFactor,         // 肉鸽试炼经验换算**系数**（按到达层数，不按分数；见下）
  starBonus,                   // 闯关模式按星级额外加成
  maxScorePerMove,
  endless3MaxScorePerMove,
  rogueMaxScorePerMove,
  minMsPerMove
}
```

公式沿用贪吃蛇：`exp = baseExp + floor(score / 模式对应除数)`。

闯关与无尽分开定除数的原因：闯关一局得分在几千量级（30 分/方块），无尽一局可打到数万分，
两者分数尺度差约 10 倍。若共用同一除数，无尽模式的单位时间经验会被严重稀释
（实测：无尽一局 3.4 万分仅得 144 经验，约 5 经验/分钟，而贪吃蛇/五子棋为 20-60 经验/分钟）。

三色爽局单独再定一个除数（1200）的原因同理：它的分数尺度比标准无尽再高约 20 倍，
取 1200 让它的**经验/分钟**与标准无尽大致同档，不因为分高就爆经验（分高但更爽，不该同时更赚）。

**肉鸽试炼是唯一不按分数的模式**——它按到达层数换算，再乘局外增益「经验共鸣」：

```
exp = baseExp + ⌊ 到达层数² × rogueExpFloorFactor（1.16）⌋ × 经验共鸣
```

层数一并受 `maxFloor`（100）截断，与服务端结算、客户端预览同源。系数取 1.16，让第 30 层 ≈ **1044** 经验，与旧版按分数换算的中位结果同档（整轮 4709 万 ÷ 45000 ≈ 1046），即改口径不改基线。

不按分数的理由见 5.7：后期得分倍率能堆到 ×45，同一层数的分差可以差几个量级（标定实测全满级玩家的整轮总分是未养成的 **72 倍**），按分结算等于把「堆分」白送成账号等级——那是满级玩家后期自动就会发生的事。改成按层数后，全满级也只是 1044 → 1764（1.69 倍），再乘「经验共鸣」满级 ×1.74 合计约 **2.94 倍**，量级从 ×73 压到个位数。

「经验共鸣」的倍率由服务端 `rogueBuffMult(saved.progress.rogue.meta, 'expboost')` 现算（未解锁返回 1），与客户端 `valueAt` 同口径（两位小数），配置在 `match3Rogue.buffs`（见 5.7 的增益表）。**共鸣树的三个机制节点都不碰经验**：丰收闭环只加精华、先手规划与时光倒流只改局内步数，所以经验只有一个倍率入口。

### 10.1 核实结论

| gameType 中文名映射（L13669） | 无 match3 条目，但调用路径不会走到 | 否 |
| 成就列表 | 服务端全量返回，v1 可能列出 match3 成就 | **是**：徽章 SVG 必须存在 |
| 对战历史 / 回放（v2 `features/replay/index.js` 按 gameType 分支，未知类型无兜底） | 未知类型会返回空 | **是**：消消乐不得进入历史 |

**结论**：v1 不会因此崩溃（其游戏列表、排行榜、统计均为硬编码固定数组），只需保证徽章资源存在、且消消乐不进历史体系。

### 10.2 硬约束（写代码前必须遵守）

1. **`games.match3` 结构对齐 `games.snake`**，不引入 `wins` / `losses` / `draws`。
   原因：总榜是把所有游戏的 `wins` 累加计算的，加入胜负字段会污染总榜数据。
2. **不调用 `updateGameStats`**（`AccountManager.js` L1323）。那是棋类胜负统计的入口，消消乐（尤其无尽模式自由结算）没有胜负概念。
3. **不写入 `games` 集合（对战历史）**。
   贪吃蛇走了这条路——`saveSnakeGameRecord` 里有 `dataStore.add('games', record)`（`GameManager.js` L1314），代价是回放模块必须为它加专门的 Canvas 分支。消消乐没有回放价值，不入历史可以直接省掉回放、观战、对战历史一整条链路。
4. **`getLeaderboard` 必须显式加 match3 分支**。
   `AccountManager.getLeaderboard` 对未知类型会 fallback 到 `games[type].wins`，而 match3 没有 `wins` → 所有人 0 分，榜单等于不存在。参照 L551-L555 与 L569-L571 的 snake 分支写法。
5. **新成就的 `badge` 必须有对应 SVG 文件**放在 `server/assets/badges/`。

## 十一、v1 到 v2 的引导方案

### 11.1 定位

- **短期**：消消乐只在 `/beta/` 与 `/preview/` 可见，v1 主入口用户看不到
- **长期**：v2 会全量替代 v1，消消乐是按面向全量玩家的正式玩法设计，数据模型、排行榜、成就一次到位

### 11.2 提示方式（两选一或叠加）

| 方式 | 实现 | 特点 |
|---|---|---|
| 一次性全服广播 | 用现有 `POST /api/chat/broadcast`，v1 客户端已有 `system_broadcast` 渲染能力 | **完全不动 v1 代码**，但只触达当时在线的人 |

### 11.3 v1 的边界

给 v1 划死一条线：**只允许加"提示 / 引导"这类零风险改动，不允许再加任何玩法。**

## 十二、分阶段实施计划

| 阶段 | 内容 | 验收 |
|---|---|---|
| P1 | 引擎全套：`grid` / `match` / `special` / `cascade` / `deadlock` | 控制台跑用例，形态识别（L/T/5/4/3）、特殊元素级联、连锁与死局判定全部正确 |

## 十三、风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| 特殊元素的级联触发写成死循环 | 页面卡死 | while 队列 + 触发次数上限保护，P1 阶段用例覆盖 |
| 无尽模式不限时被脚本刷分 | 排行榜失效 | 9.4 的三条校验必须和上报接口同时上线，不能延后 |
| 成就条件求值逻辑不支持新字段 | 成就无法解锁 | 实现时同步在 `checkAchievements` 补条件分支（见 9.6 注意项） |
| 洗牌后仍为死局 | 玩家卡死 | 洗牌后强制复检，复检失败则重新洗牌（设上限） |
| 动画与逻辑耦合导致改一处崩一处 | 维护困难 | 引擎层不碰 DOM，动画只在 `board.js` 编排 |
| 前期把消消乐塞进统一游戏大厅 | 结构别扭、返工 | 已决策走独立导航项，不并入大厅 |
| 高自由度棋盘容易配出不可通关的关卡 | 卡关、玩家流失 | 增加开发期关卡校验脚本：检查 mask 合法性、目标是否可达、初始无三连且有可行步 |
| 异形棋盘只靠肉眼验证容易漏错 | 上线后才发现形状或下落错位 | P1 用例必须覆盖挖洞与分仓棋盘；P2 对矩形 / 异形 / 分仓各跑一次 |
| 分仓棋盘整体洗牌破坏其他区域局面 | 玩家体验受损 | 洗牌与死局判定均以「区域」为粒度（见 3.6） |
| 肉鸽养成的后期爆发把经验一起顶上去（旧口径单轮约 1.05k → 76.9k，约 ×73） | 账号等级经济被「打深」的复利冲垮 | **已解决（v1.18）**：经验改按到达层数换算（与精华同口径），倍率交给局外增益「经验共鸣」且封顶 ×1.74，合计约 2.94 倍（见 5.7 / 9.5）；层数另有 `floor ≤ moves` 与 `maxFloor` 兜底 |
| 共鸣树里的机制节点让层数上不封顶（「时光倒流」每轮多一条命） | 精华与经验的层数基数被抬高 | **已解决（v1.19）**：三个机制节点都固定 Lv.1、不可升级，时光倒流每轮只 1 次；标定档「共鸣树全点亮」中位 31 层（+1）、「树 + 祝福全满」38 层（与只有祝福全满的 39 层同档），见 5.7 的标定结论 |
| 客户端 `perks.js` 与服务端 `config.js` 是两份手工同步的配置，改树只改一边 | 界面能买、服务端拒绝（或反之），两端口径分歧 | 服务端 `match3Rogue.buffs` 的 `kind` / `requires` / `mechanics` 必须与 `META_BUFFS` 一起改（见 5.7「服务端为共鸣树补的三处」）；标定脚本的三类一致性检查会在改坏时直接抛错 |
