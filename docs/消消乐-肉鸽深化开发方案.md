### 1.2 与主流肉鸽的特征差距对标

对标对象：《杀戮尖塔》（路线分支）、《以撒》（道具质变）、《哈迪斯》（神赐 build）、《小丑牌》（强机制牌）。评分 0–3（0=无，1=雏形，2=基本具备，3=成熟）。

| 肉鸽核心特征 | 典型表现 | 现状 | 评分 | 差距根因 |
|---|---|---|---|---|
| **随机地图/路线** | 节点 DAG、分叉选路、房间类型分布 | 固定线性爬层，无路线 | **0** | 层只是一个递增数字，没有「地图」对象 |
| **房间类型多样** | 普通/精英/Boss/事件/商店/宝藏/篝火 | 只有「分数层」+ 层间三选一 | **0** | 30 层是同一玩法循环的重复 |
| **地形/局面随机** | 每房间布局、机关、敌我配置不同 | 每层都是**完整 8×8 标准盘** | **0** | 引擎已有 mask/blockers，肉鸽完全没接 |
| **角色/职业差异** | 不同起手与被动，玩法流派不同 | 无角色，每轮起手完全相同 | **0** | 缺少 run 级「身份」 |
| **策略选择分支** | 路线、资源、风险收益、删牌等多决策点 | 仅层间三选一处决策 | **1** | 决策点单一且只有增益无代价 |
| **build 质变（遗物/道具）** | 少量但能改变规则的强机制物品 | 仅「同色磁石」1 张改机制，其余全是数值加减 | **1** | 祝福池几乎无 hook，无「遗物层」 |
| **随机事件** | 多选项、有代价、结果可能未知 | 仅「收集任务」，纯增益、无选项 | **1** | 无事件数据结构与事件 UI |
| **敌人/Boss 对抗** | 有对抗对象、阶段、技能、击败通关 | 无敌人，纯分数达标 | **0** | 终局是「打不动的数值墙」而非 Boss |
| **局内经济/商店** | 局内货币、消费抉择、刷新 | 只有局外精华，局内无货币 | **0** | — |
| **永久死亡** | 死亡即重开，局内积累全失 | 有，但容错手段偏多且常驻 | **2** | 死亡缺戏剧性与回顾 |
| **胜利目标** | 击败最终 Boss 即「通关」 | 只有「打到打不动」，无胜利 | **0** | 缺少顶层目标 |
| **难度阶梯（进阶）** | 通关后自主选择递增修正 | 单一固定曲线 | **0** | 硬核玩家无追求，30 层后即终点 |
| **局外 meta 成长** | 跨局解锁与增强 | 精华 + 共鸣树 | **3** | 已成熟 |
| **随机性可复现** | seed、可标定 | runRng + 快照恢复 | **3** | 已成熟 |

**结论：当前玩法准确的描述是「带三选一增益的限步冲分」，它具备 roguelite 的 meta 外壳（死亡重开 + 局外成长），但缺少肉鸽的肉——结构随机、路线抉择、机制质变与对抗目标。** 13 项核心特征里 6 项为 0、4 项为 1。

### 1.3 五个核心病灶

1. **结构不随机，只随机数值。** 每轮的「形状」完全一样：一条直线、8×8 满盘、纯刷分。玩家第 1 层和第 25 层玩的是同一个局面模板，差异只是数字变大。
2. **节奏单一导致疲劳。** 循环恒为 `标准盘→刷分→达标→三选一→下一层`，30 层重复同一节拍，没有「这一层要换思路」的停顿与惊喜（事件/商店/篝火）。
3. **build 只有量变没有质变。** 15 条祝福里 14 条是「步数 +N / 倍率 ×N / 送 N 个特殊元素」，叠加后期望的是「×45 倍率」而不是「我组出了一套连锁永动玩法」。
4. **没有对抗与胜利，只有猝死。** 终局由 `goalGrowth 1.33` 指数曲线与可达分平台在 28–30 层交汇决定，玩家是「被数值撞死」，而不是「败给某个 Boss」或「通关后见好就收」。缺少正向胜利闭环。
5. **决策面太窄。** 玩家长线只决策「三张里拿哪张」，不决策路线、不管理局内资源、不在事件里权衡代价、不按角色规划流派。策略深度撑不起「肉鸽」应有的重玩价值。

## 二、设计总纲

### 2.1 目标定位

把「肉鸽试炼」从娱乐菜单里的一个**冲分小游戏**，升级为一条有**地图、有角色、有 build 协同、有 Boss 可通关、有进阶挑战**的完整 roguelite 主线，同时保留「15–30 分钟一局、消消乐操作零学习成本」的轻量底色。

一句话体验目标：

> **每一轮都在不同的地图上做十几道「往哪走、拿什么、赌不赌」的选择题，用消消乐的连锁把一套当场拼出来的 build 滚成雪球，去击败每 10 层一个的 Boss；死了就带着精华重开，解锁角色与进阶再冲一次。**

### 2.2 新一轮核心循环

```
选角色（P5）
   │
   ▼
生成随机地图（节点 DAG：普通/精英/事件/商店/宝藏/篝火/Boss）
   │
   ├─ 在分叉点选择下一个节点（路线决策）
   ├─ 战斗节点：在「区域地形 + 多目标」的棋盘上消除（操作层）
   │     └─ 层内随机任务 / 遗物触发 / Boss 干扰
   ├─ 事件节点：2–3 个带代价的选项（风险决策）
   ├─ 商店节点：花局内金币买祝福 / 遗物 / 资源
   ├─ 宝藏节点：白拿遗物
   ├─ 篝火节点：恢复 or 强化一张祝福
   └─ 精英/Boss：高难度 + 更好奖励 / 通关判定
   │
   ▼
击败第 3 个 Boss（第 30 层）= 本轮「通关」
   └─ 可选：进入无尽深渊继续冲（沿用现有无限层与最高分榜）
   │
死亡/通关 → 结算精华（局外）→ 解锁/升级/进阶 → 再来一轮
```

### 2.3 三层成长边界（务必守住，避免系统互相打架）

| 层 | 生命周期 | 载体 | 获取 | 性质 |
|---|---|---|---|---|
| **局内临时资源** | 单层 | 步数、任务奖励 | 消除/任务 | 即得即用 |
| **本轮 run build** | 单轮，死亡清空 | 祝福（数值，可叠加）+ **遗物（机制，少量）** + **局内金币** + 角色被动 | 三选一/商店/事件/宝藏/Boss | 主攻 build 多样性 |
| **跨轮 meta** | 永久 | 精华、共鸣树、祝福解锁/升级、**角色解锁**、**进阶等级** | 结算 | 控强度上限（标定 +30% 层），主要给目标与便利，不给碾压 |

原则：**强度大头放在「局内 build」，meta 只给起点与广度（解锁更多牌/角色/进阶），不让精华直接买出碾压数值**——延续 5.7 标定结论（共鸣树只 +1 层，祝福满级 +9 层）。

### 2.4 四条工程原则（沿用既有）

1. **数据驱动**：地图规则、层类型、事件、遗物、角色、进阶全部是 `config/perks` 式的纯数据数组，加内容不改渲染分支。
2. **纯逻辑可标定**：推导放纯函数模块，`match3-rogue-balance.mjs` 必须能在无 DOM 下模拟新机制（地图生成、遗物 hook、Boss 血量）。
3. **服务端权威**：meta 经济、解锁、进阶、通关结果在服务端校验；局内过程只暂存、终局结算。
4. **最小侵入引擎**：能用现有 board API（`getState / addMoves / setScoreMult / addSpecials / shuffle / lock` 与 payload 的 `mask / blockers / colors / colorWeights`）实现的，不改引擎；确实要加的引擎能力集中在少数几个新方法（主要是 `addBlockers` 与几个 hook）。

## 三、核心系统实现路径

> 每个系统统一给：**现状/差距 → 设计 → 数据结构 → 落点 → 引擎改动量**。
> 标注的优先级（P0–P6）对应第六章排期。

### 3.1 随机地图与节点分支（P0）

**这是「肉鸽味」最大的一块，也是其它所有层类型的承载，必须最先做。**

#### 设计
- 一轮 run 不再是「第 N 层」一条直线，而是一张**纵向节点图**（参考杀戮尖塔）：横轴是「同一深度的若干并行节点」，纵轴是深度。玩家从底部起点出发，每层在当前节点连出去的 1–3 个下游节点里**选一个**，被选中的路径之外的节点永久关闭。
- **Boss 节点固定在深度 10 / 20 / 30**，且 Boss 前一层必然全连 Boss，保证一定能打到。三个 Boss 把 run 切成三个「区域（biome）」。
- 节点类型与分布由生成器按规则保证（不是纯随机撒点）：普通战斗占多数；精英每区域 1–2 个；事件每区域 2–3 个；商店与篝火在 Boss 前各保证至少 1 个且位置可规划；宝藏稀有。
- 进游戏先展示**整轮地图**（战争迷雾：已走过/可选相邻可见，未到达的高层只显类型图标或完全遮蔽，可由角色/meta 控制预览层数）。每次结算节点后回到地图，高亮可前进的节点。

#### 数据结构（新增 `mapgen.js`，纯函数）

```js
// 节点类型
export const NODE = {
  BATTLE: 'battle',     // 普通战斗（现有刷分层）
  ELITE: 'elite',       // 精英：高目标 + 障碍，奖励更好
  BOSS: 'boss',         // Boss：固定深度，通关判定
  EVENT: 'event',       // 随机事件
  SHOP: 'shop',         // 商店
  TREASURE: 'treasure', // 宝藏：白拿遗物
  REST: 'rest',         // 篝火：恢复 or 强化
};

// 一个节点
// { id, depth, type, biome, next:[nodeId], state:'locked|open|done|skipped', seed, payload? }

/**
 * 程序化生成一张 run 地图
 * @param {object} rng - runRng（同一张图可被 seed 复现）
 * @param {object} opts - { ascension, character }
 * @returns {{ nodes:Node[], start:string[], bosses:string[], depth:number }}
 */
export function generateMap(rng, opts) { /* ... */ }
```

生成约束（在纯函数里实现，标定脚本可统计「类型分布/可达性」）：

- 深度 0 为单一起点；深度 10/20/30 为单一 Boss；
- 每个非终点节点的 `next` 数量 1–3；任意深度的节点都能到达该区域 Boss（连通性校验）；
- 相邻深度连边时限制「跨度」（只连下一排邻近列），形成真正的分叉而不是全连通；
- 类型配额：战斗 ≥55%，精英每区域强制 1–2，事件每区域 2–3，商店/篝火 Boss 前各 ≥1，宝藏每区域 ≤1；
- 精英/Boss 的类型一旦定下不可被普通节点挤出（先放骨架节点，再用战斗/事件填充）。

#### 落点与改动量
- 新增 `mapgen.js`（纯逻辑 + 地图连通性/配额的自检，可被标定脚本直接跑）。
- `mode-rogue.js` 把「floor 数字 + mountFloor」重构为「**当前节点 node + mountNode**」：`floor` 改由 `node.depth` 推导（精华/经验/目标曲线全部继续用 depth，旧公式不动）；层间从「直接三选一开下一层」改为「回地图 → 选节点 → 按节点类型进入对应 handler」。
- 新增地图视图组件（可放在 mode-rogue 内或新建 `map-view.js`），用绝对定位/SVG 画节点与连线；数据驱动，复用 codex 树的纯 DOM+CSS 经验，不引框架。
- 续存 `toSession` 增加 `map`（节点图）、`nodeId`（当前节点）、`openIds`（可前进节点）。地图用 seed + 生成参数即可重建，**默认只存 seed 与已变更状态（done/skipped）**，减小存档体积。
- **引擎改动量：零**（纯模式层与数据层）。整体工作量 **L**（UI 占大头）。

### 3.2 层类型、区域地形与多目标（P0）

**让棋盘本身「随机」起来，并把现成的 mask / blockers / 多目标引擎用进肉鸽。**

#### 现状/差距
- [levels.js](file:///d:/工程文件/网页游戏/client-v2/src/games/match3/config/levels.js) 已有 10 种异形 mask（菱形/十字/环形/心形/阶梯/沙漏/蝴蝶结/三角/城堡/花朵）与冰🔒/🔒/🪨三种障碍；
- 棋盘 payload 已支持 `mask`、`blockers`，state 已记录 `collected`、`blockersCleared`；
- 多目标判定在 [mode-level.js](file:///d:/工程文件/网页游戏/client-v2/src/games/match3/modes/mode-level.js) 已有 `score / collect / clearBlockers` 三种判定（L68-81）；
- **但肉鸽的 `floorOptions` 只产出满盘 8×8 + 单一 score 目标**（perks.js L442-471），上述能力一个没用。

#### 设计

**（a）三个区域（biome）绑定地形与障碍**，随深度切换，提供视觉与玩法节奏：

| 区域 | 深度 | 地形（mask 池） | 障碍 | 基调 |
|---|---|---|---|---|
| 🍃 风语平原 | 1–10 | 完整矩形为主，偶发十字/菱形 | 无 / 少量锁链 | 教学、铺 build |
| ❄️ 霜蚀冰原 | 11–20 | 菱形/环形/沙漏 + 冰块、锁链 | 中量冰块（hp2） | 地形切碎、连锁受限 |
| 🌋 熔核深窟 | 21–30 | 分仓/蝴蝶结/城堡 + 石头 | 大量石头（hp3）+ 冰 | 多目标、要规划清障 |

mask 仍取 **8×8 等效规模**（避免动 `ROGUE.rows/cols` 与精华曲线）；异形用 9×9 mask 时通过 `BOARD_LIMITS` 内的尺寸生成，目标值按「可玩格比例」折算（levels.js 已有 `SHUFFLE.minPlayableRatio` 与按形态分档的标定经验）。

**（b）层目标从单一 score 扩展为 1–2 个 goals**，直接复用闯关模式目标结构：

```js
// 普通层：随区域在三类目标里按权重抽（不再永远是 score）
//   score           —— 现有
//   collect 色 N    —— 复用局内任务的颜色/need 曲线（questFor），但升级为「过关硬目标」
//   clearBlockers N —— 冰原/深窟主打
// 精英/Boss：score + 一个条件目标（双目标），见 3.3
```

「层内随机任务」（现有 quest）**保留为额外的软目标/奖励**，与硬目标分离：硬目标不过 = 本轮结束；软任务不惩罚、给即时奖励。这样既加多目标，又不增加死亡压力。

#### 数据结构（扩展 perks.js / config.js）

```js
// config.js 新增
export const ROGUE_BIOMES = [
  { id: 'plain',  from: 1,  to: 10, masks: [null],            blockers: { lock: 0 },  goalKinds: ['score','collect'] },
  { id: 'frost',  from: 11, to: 20, masks: ['diamond','ring','hourglass'], blockers: { ice: 4, lock: 2 }, goalKinds: ['score','collect','clearBlockers'] },
  { id: 'core',   from: 21, to: 30, masks: ['bowtie','castle','flower'], blockers: { stone: 5, ice: 3 }, goalKinds: ['score','clearBlockers','collect'] },

// floorOptions 增加返回：mask / blockers / goals（数组）；旧调用方只取 moves/colors 等不受影响
```

#### 落点与改动量
- `perks.js.floorOptions` 增加 `mask/blockers/goals` 推导（按 node 的 biome/type + runRng 抽取），**纯函数**。
- `mode-rogue.js`：① payload 透传 `mask/blockers`（board 已支持）；② 过关判定从「`score>=goal`」改为复用 mode-level 的多目标判定（把那 ~10 行判定抽成 `goals.js` 共享小模块，闯关与肉鸽都引，避免两份漂移）；③ 侧栏目标区从单行目标改为多目标列表（复用 mode-level 的 goal UI）。
- 关卡目标的 score 数值在异形/障碍盘上要**重新标定**：扩展标定脚本支持 mask/blockers（脚本里 `playFloor` 目前写死 8×8 满盘，需接 mask 与 placeBlockers）。
- **引擎改动量：零**（mask/blockers/goals 引擎都已支持）。工作量 **L**（标定与多目标接线为主）。

### 3.3 精英层与 Boss 层：胜利闭环（P1）

**把「数值墙猝死」改造成「打 Boss / 战死」，给出正向胜利。**

#### 精英层
- 每区域 1–2 个，图标 ⚔️：进入前**可见预警**（高风险，玩家自主选路绕开或挑战）。
- 规则：双目标（score + collect/clearBlockers）、目标系数 ×1.25–1.5、带预设障碍；奖励更厚——**保底稀有(rare)以上祝福 + 局内金币 + 更高遗物掉率**。
- 数据上就是 `NODE.ELITE` 走一套更紧的 `floorOptions` 系数与一个加权奖励表，无引擎改动。

#### Boss 层（第 10 / 20 / 30 层）

**分两期实现，避免一上来做复杂 Boss AI：**

- **P1（数值 Boss，先打通胜利闭环）**：Boss = 「高血量 + 多阶段目标 + 固定机关盘」。
  - Boss 有 HP，**消除得分转化为对 Boss 的伤害**（伤害 = 本层得分，HP 用现有 `goalOf` 在 10/20/30 层的目标值放大设定，沿用已标定曲线，不新增经济尺度）；
  - 棋盘预设强障碍布局（冰原 Boss 全图冰块、深窟 Boss 分仓石头阵）；
  - 阶段阈值（如 HP 66% / 33%）触发一次性机关：注入额外障碍 / 临时锁定一种颜色（已有 colorWeights 的反向用法）/ 收走 N 步——用现有 board 能力即可表现；
  - 步数内打空 HP = 击败：第 10/20 层给**Boss 遗物宝箱（三选一遗物）**后进入下一区域；**第 30 层击败 = 本轮通关**。
- **P1.x（行为 Boss，后续迭代）**：给 board 增加 `addBlockers(list)`（层中注入障碍，目前只有开局 `placeBlockers`）与一个 `onPhase` 钩子，让 Boss 每隔 K 步主动施法（冻结随机格、封锁、遮挡）。这是本方案唯一明确要新增的引擎写操作，接口与现有 `addSpecials` 对称，工作量可控。

#### 通关与「无尽深渊」
- 第 30 层 Boss 倒下 → **胜利结算页**（区别于现「💀 本轮结束」）：显示「🏆 通关」、用时、build、遗物、路线图。
- 胜利后给二选一：**结束本轮领精华**（标准肉鸽的「见好就收」）或**继续深入无尽深渊**（深度 31+，回到现有无上限层数 + 最高分榜，精华按通关一次性结算、深渊段只给少量衰减增量，防止与最高分互刷，需服务端封顶）。
- 服务端结算新增 `win` 与 `ascension`、`bossKills`；精华公式仍以「到达层数」为主，但**通关给一笔固定通关奖励精华**（在 `match3Rogue` 配置新增 `winBonus`），引导「打 Boss」而非「刮痧绕 Boss 堆层」。

#### 落点与改动量
- 新增 `boss.js`（Boss 定义：三个 Boss 的 id/名称/HP 系数/阶段机关/掉落表，纯数据 + 伤害换算纯函数）。
- mode-rogue 增加 Boss 节点 handler、Boss 血条 UI、阶段机关调度、`winRun()`（与 `finishRun()` 并列）。
- 服务端 `match3_game_end` 与 `addRogueEssence` 增加 win/通关奖励分支；新增通关成就。
- 引擎：P1 **零改动**；P1.x 新增 `addBlockers`（S）。整体 **L**。

### 3.4 随机事件系统（P2）

**补上肉鸽标志性的「问号房」：有选择、有代价、结果可能未知。**

#### 设计
- `NODE.EVENT` 不进棋盘，进入后是一张事件卡：插画位(用 emoji)+ 情境文案 + **2–3 个选项**。
- 消消乐语境里没有「血量」，用三类资源承担代价：**步数（下一层起手步数）/ 护盾与容错 / 局内金币与遗物**。
- 选项类型：确定增益（付出代价换祝福/遗物/金币）、赌博（runRng 决定好坏，概率可见或隐藏）、零和（牺牲一项资源换另一项）、离开（无事发生）。
- 事件按深度/区域加权抽取，部分事件带前置条件（持有某遗物/金币达到阈值才出现某选项）。

#### 数据结构（新增 `events.js`）

```js
export const EVENTS = [
  {
    id: 'wandering_merchant_lost', icon: '🎒', weight: 10, minDepth: 2,
    text: '一个迷路的商队愿意用稀有物资换你一些「脚力」。',
    choices: [
      { text: '用下一层 −3 步，换 1 件随机遗物',
        when: (s) => s.coins >= 0,
        apply: (ctx) => { ctx.bonus.moves -= 3; grantRelic(ctx, 'random'); } },
      { text: '花 40 金币买一个随机祝福（加入本轮）',
        when: (s) => s.coins >= 40,
        apply: (ctx) => { ctx.coins -= 40; grantPerk(ctx); } },
      { text: '离开', apply: () => {} },
    ],
  },
  {
    id: 'cursed_altar', icon: '🗿', weight: 8, minDepth: 11,
    text: '诅咒祭坛：献祭一半护盾，赌一次稀有三选一。',
    choices: [
      { text: '献祭（无护盾则改为下一层 −4 步）',
        apply: (ctx) => ctx.rng.chance(0.7) ? grantRarePerk(ctx) : curse(ctx) },
      { text: '摧毁祭坛（拿 25 金币）', apply: (ctx) => { ctx.coins += 25; } },
    ],
  },
  // …目标 20–30 个事件
];
```

- 所有 `apply` 只改 run 状态（`bonus/coins/relics`）或调度授予，不碰 DOM；随机一律走 `runRng`（可复现、可标定）。
- 事件结果需要二次确认与结果文案；坏结果不能直接判死（肉鸽事件是「扰动 build」，不是「随机删档」）。

#### 落点与改动量
- 新增 `events.js`（数据 + `rollEvent(rng, runState)` 纯函数）、事件卡 UI（复用 modal）。
- mode-rogue 增加 EVENT 节点 handler；事件对 `bonus` 的修改天然进 `floorOptions` 与续存。
- **引擎改动量：零**。工作量 **M**（内容填充是长尾，先上 12 个事件，后续热更式加数据）。

### 3.5 遗物：机制性被动（P3）

**解决 build「只有量变」的核心。参考《杀戮尖塔》遗物 / 《以撒》道具：数量少、不可叠加、改规则、能组成流派。**

#### 与祝福的分工
- **祝福（PERKS）**：数值、可在三选一里反复叠加，是 build 的「数值底盘」。
- **遗物（RELICS，新增）**：机制、每轮每件最多 1 个、一轮通常持有 3–6 件，是 build 的「玩法引擎」。遗物**不进三选一池**，只从宝藏/Boss/事件/商店获得。

#### 触发模型（尽量不改引擎）
遗物通过在**既有钩子**上挂判定实现。mode-rogue 已经持有 `onUpdate(info)`（含 `score/maxCascade/collected/movesLeft`）与 board 的 `onStep({ cascade, gained })`，多数遗物零引擎改动即可做：

| 钩子 | 可实现的遗物示例 | 是否要改引擎 |
|---|---|---|
| 每层开局 `onFloorStart` | 「每层出 1 个彩球」「起始多 2 步但目标 +10%」 | 否（走 bonus/specials） |
| 每次走子后 `onStep` | 「连锁 ≥4 返还 1 步（每层限 3 次）」「连锁 ≥5 本步得分 ×2」 | 否（onStep 已给 cascade/gained + addMoves/setScoreMult） |
| 收集计数 `onUpdate.collected` | 「累计消除某色 20 个，立即造 1 个炸弹」 | 否（addSpecials） |
| 过关时 `onFloorClear` | 「每层未用过洗牌，过关返 10 金币」「满血（满步）过关下一层 +1 步」 | 否 |
| 商店/事件折扣 | 商店价格 −20% | 否 |
| 三选一时 | 「每次三选一可重随 1 次」「三选一额外 +1 选项」 | 否（改 rollPerks 调用参数） |
| **走子中改棋盘生成/命中** | 「特殊元素爆炸半径 +1」「彩球同时清两色」「概率免疫障碍伤害」 | **需要引擎 hook**（少量） |

需要引擎的部分，统一在 board 创建时接收一个 `relicHooks` 回调集合（`onBeforeResolve / onAfterCascade / onSpecialTrigger` 等），由 cascade 在对应位置调用；**引擎只负责回调，不含任何遗物逻辑**，遗物仍定义在客户端数据里。第一期可只做「零引擎改动」那一档（覆盖 70% 有趣遗物），引擎 hook 放第二期。

#### 数据结构（新增 `relics.js`）

```js
export const RELICS = [
  { id: 'infinite_chain', icon: '⛓️', name: '无尽锁链', rarity: 'rare', max: 1,
    desc: '连锁达到 4 时返还 1 步（每层最多 3 次）',
    trigger: 'onStep',
    onStep(ctx, step) {
      if (step.cascade >= 4 && ctx.usedThisFloor < 3) { ctx.board.addMoves(1); ctx.usedThisFloor++; }
    } },
  { id: 'twin_rainbow', icon: '🌈', name: '双色棱镜', rarity: 'epic', max: 1, engineHook: 'rainbow',
    desc: '彩球交换时同时清除两种颜色（需引擎 hook）' },
  // …目标首发 18–24 件，按「连锁流 / 特殊元素流 / 经济流 / 生存流」分组，确保能拼出 ≥4 种流派
];
```

#### 协同设计（制造「组 build」乐趣）
- 遗物之间、遗物与祝福之间设**协同与拮抗**：例如「无尽锁链（连锁返步）」+「同色磁石（更容易长连锁）」+「极简主义（降色）」组成「连锁永动流」；「双色棱镜」+「彩球礼物/彩虹风暴」组成「彩球清屏流」。
- 三选一与商店在信息上提示协同（已持有相关遗物时，关联祝福加「可联动」标记），引导新手、不强制。

#### 落点与改动量
- 新增 `relics.js`（数据 + hook 分发纯函数）；遗物槽 UI（侧栏，复用祝福 chip 样式）、遗物图鉴并入 codex。
- 本轮持有物 `relics: []` 进 bonus 旁路（独立数组，不污染数值 bonus）与续存。
- 局外 meta 增加「已发现遗物」集合（图鉴/掉落池解锁，可用精华解锁或事件/Boss 首次发现解锁，二选一，见 4.2）。
- 工作量：零引擎档 **M**，含引擎 hook 档 **L**。

### 3.6 局内金币与商店（P4）

#### 设计
- 新增**局内货币金币 🪙**：战斗/精英/任务/事件掉落，**本轮结束清零**，与局外精华完全隔离（延续 5.7「只发精华、不与道具经济互窜」原则，金币是更里层的一次性资源）。
- 掉落：普通层过关 +8～15、层内任务 +5、精英 +30、事件 ±、剩余步数折算（鼓励打得好）。数值在标定脚本里以「场均金币 / 商店均价」校准，保证一轮能在商店做 2–4 次有效消费。
- **商店节点 🛒**（每区域 Boss 前必有 1 个）：货架 4–5 格，内容随机：
  - 卖祝福（把一张祝福加入本轮三选池并立即生效一张，或卖「下次三选一额外选项」）；
  - 卖遗物（1 件标价遗物 + 1 件高价随机遗物）；
  - 卖资源：+N 步（仅下一层）/ 1 次护盾 / 1 次重随三选一；
  - **移除服务（消消乐版「删牌」）**：花高价「封禁」本轮一条不想要的祝福（返还少量精华或换成金币），让 build 更聚焦——这是杀戮尖塔删牌的等价物。
  - 可花少量金币「刷新货架」1–2 次。
- 价格、货架槽位、刷新费全部走配置表，遗物/祝福按稀有度定价。

#### 落点与改动量
- run 状态新增 `coins`（与 baseScore 同级，非 bonus），进 `toSession`；新增 `shop.js`（货架生成纯函数 + 购买逻辑）、商店 UI。
- 购买祝福复用 `perk.apply(bonus,…)`；购买遗物入遗物槽；封禁祝福改 `picks` 计数与一个 `banned[]`（rollPerks 过滤）。
- 金币只在局内有意义，**不上报服务端、不参与反刷分**（终局不兑换精华，避免刷金币旁路；如要给「剩余金币少量折算精华」必须设很低系数且服务端封顶，默认不做）。
- **引擎改动量：零**。工作量 **M**。

### 3.7 篝火与宝藏（P2）

- **宝藏 💎**：免费节点，开 1 件随机遗物（首次通关某区域前可为「祝福三选一」兜底，降低空过率）。纯奖励、零风险，作为路线上的「甜点」。
- **篝火 🔥（休整抉择，二选一）**：
  - **休整**：补资源——下一层起手 +N 步 / 获得 1 次护盾（容错回血，消消乐的「血」就是步数/护盾）；
  - **锻造**：不回血，改为从本轮已持有的祝福里挑 1 张**临时升级**（本轮内该祝福视为高 1 级，用 `valueAt(perk, lv+1)` 实现），强化滚雪球但放弃续航。
  - 这是典型的「现在保命 vs 以后更强」的资源抉择，且 Boss 前的篝火位置让抉择更有分量。
- 临时升级只活在本轮（`picks` 里加一个 `upgradedIds` 运行时集合，不写局外 meta）。
- 工作量 **S–M**，零引擎改动（强化复用现有等级曲线）。

### 3.8 角色 / 职业（P5）

**解决「每轮起手完全相同」，给流派一个入口身份。**

#### 设计
首发 3 个角色，差异靠「起始 bonus + 固定起始祝福/遗物 + 一条角色被动」，全部用数据描述，复用 `createBonus / applyMetaBuffs` 注入点：

| 角色 | 风格 | 起手差异（示例，需标定） | 被动（一个机制遗物） |
|---|---|---|---|
| 🔥 连锁术士 | 连锁滚雪球 | 6 色、10 步；起始祝福「熟练手法」；起始 1 彩球 | 连锁 ≥4 返步（等同无尽锁链，角色自带） |
| 🛡️ 壁垒守卫 | 稳健生存 | 6 色、**12 步**；起始 1 护盾；倍率 ×0.9 | 每层第 1 次死亡必定免死且不耗护盾 |
| 🧲 调色术士 | 色彩操控 | **5 色起手**、10 步；起始祝福「同色磁石」；目标 +10% | 磁石每区域可重新锁色 1 次 |

- 解锁方式：默认开放 1 个，其余用**通关/成就**解锁（如「连锁术士初始可用」「壁垒：累计到达 20 层」「调色术士：用磁石 build 通关一个 Boss」），**不用精华买强度**，角色只是玩法入口。
- 角色选择在 run 开始前；选择写入 session 与终局上报，按角色统计胜率/最高进阶（成就与日后榜单用）。
- 角色被动统一实现为「角色自带的、不可移除的遗物」，直接复用遗物系统（3.5），不再单独造一套被动引擎。

#### 数据结构（新增 `characters.js`）

```js
export const CHARACTERS = [
  { id: 'sorcerer', icon: '🔥', name: '连锁术士', unlock: null,
    startBonus: { }, startPerks: ['focus'], startRelics: ['infinite_chain'],
    desc: '擅长用长连锁换取额外步数。' },
  { id: 'guardian', icon: '🛡️', name: '壁垒守卫', unlock: { stat: 'bestFloor', value: 20 },
    startBonus: { moves: 2 }, startPerks: [], startRelics: ['guardian_ward'],
    scoreMultStart: 0.9 },
  { id: 'palette', icon: '🧲', name: '调色术士', unlock: { winBoss: 1 },
    startBonus: { colorCut: 1 }, startPerks: ['magnet'], startRelics: ['recolor_pact'] },
];
```

#### 落点与改动量

### 3.9 永久死亡与硬核模式（P6）

- 保留 roguelite 定位（meta 成长是商业化与留存的合理选择），但**厘清容错来源、强化死亡仪式感**：
  - 把「免死/护盾/时光倒流」明确为**局内稀缺资源**（主要来自篝火/商店/事件/精英），削弱其「局外常驻、每轮白给」的占比——共鸣树保命流可保留但定位为新手拐杖；
  - **死亡结算页升级为「本轮墓志铭」**：走过的路线图缩略、最终 build 与遗物、关键数字（最高连锁、最长连锁返步次数、精英/Boss 击杀）、死亡原因（差多少分/死在哪个区域哪个节点）、与历史最佳对比，以及「再来一轮」主按钮（弱化「返回」）。
- **硬核模式（Hardcore，可选开关）**：禁用全部局外养成加成（`applyMetaBuffs` 空跑）、容错资源更少、地图精英/Boss 更密；独立榜单与专属成就，但**精华奖励更高**（风险对价）。它满足想要「纯 roguelike」的玩家，也让高水平玩家有公平竞技口径。
- 死亡→重开转化是肉鸽留存核心，埋点统计「死亡结算页 60 秒内点击再来一轮比例」（见第七章指标）。
- 工作量 **S**（结算页与开关为主）。

### 4.7 存档体系：版本号 / 两类存档 / 迁移脚本 / 完整性校验

> 本节是 P0 地图结构改造的**前置基础设施**，必须与 P0 同批落地：地图、遗物、金币、事件等一大批新字段同时进存档，没有版本与迁移机制，灰度发布、版本回滚、半道更新必然炸档。

#### 4.7.1 现状核查（先厘清事实，避免在假设上设计）

| 项 | 现状（已核查代码） | 风险 |
|---|---|---|
| 局外 meta 版本 | 客户端 `emptyMeta()` 与服务端 `_normalizeRogue` 都**硬编码 `version: 1`**，没有任何迁移逻辑 | 加字段只能靠 `normalizeMeta` 的 spread 兜底；两端各写各的，版本号不会随结构升级 |
| meta 归一化方式 | 两端都是**白名单重建**（按已知 id/字段重新拼对象） | 未知字段在归一化回写时被丢弃——回滚期间新版数据会被老版服务端写没 |
| 局内 session 版本 | **没有版本字段**；服务端只校验 `mode` 一致与 `maxBytes`（32KB），内容不解释（[server.js](file:///d:/工程文件/网页游戏/server/server.js) L4047-4087） | 新旧结构只能靠 `resumeRun` 里手工 `\|\| 默认值` 硬扛；结构不兼容时静默读出错局面 |
| 完整性校验 | **全项目不存在任何 CRC / checksum / 哈希**（grep 命中的 hash 全是 git 提交号与路由 hash） | localStorage 被截断/写坏时，坏数据会直接进迁移与续玩 |
| 现有的"校验"实际是 | 服务端权威 + `num(v,min,max)` 区间裁剪 + 结算反刷分（步数/耗时/单步分） | 能防数值异常与刷分，**不能检测存档损坏** |
| 两类存档分离 | 物理上已分离：`rogueMeta`（本地缓存）与 `rogueSession`（续存）两个 key；服务端同文件内 `rogue` 段与 `sessions.rogue` 段 | 分离已存在但**没有成文约束**，新功能（事件状态等）很容易图省事写进 meta |

#### 4.7.2 双版本号设计

局外、局内两类存档的更新节奏与权威方不同，**各自独立一个版本号**，不共用：

```js
// server/config.js → match3Rogue（权威，随 match3_progress 下发）
saveVer: 2,
// client config.js → ROGUE_META.saveVer（离线/游客兜底镜像，与服务端手工同步）

// 局内 session 不依赖服务端配置（离线也要能判定），常量写在客户端 config.js
SESSION_SCHEMA_VER: 2,   // 无版本字段的老 session 一律视为 1
```

- 现有的 `version: 1` 字段不删：读到 `version` 视作 `saveVer` 的别名（`saveVer = raw.saveVer || raw.version || 1`），避免与关卡的 `schemaVersion` 概念混淆，文档与新代码统一改称 **saveVer**。
- **升级版本号的时机**：只在"读旧数据会产生错误语义"时升号（新增/删除字段、改字段含义、改结构）；纯追加且老代码读到也无害的字段，可在同一 saveVer 内由迁移补默认。每次升号必须同时提供 `from→to` 迁移与 fixture（见 4.7.4）。

**加载时的三向版本判定**（meta 与 session 同一套规则、各自实现）：

```
存档版本 === 当前版本      → 直接使用
存档版本  <  当前版本      → 按 MIGRATIONS 链式迁移（只增不改不删），完成后盖当前版本号
存档版本  >  当前版本      → 回滚场景：不迁移、不报错、不判损坏（具体策略两类存档不同，见 4.7.3 / 4.7.4）
```

#### 4.7.3 两类存档严格分离（成文约束，防两类高频事故）

| | 局外永久存档（meta） | 局内临时续存（session） |
|---|---|---|
| 内容 | 精华 / 共鸣树 / 祝福等级 / 里程碑 / **已解锁角色 / 已发现遗物 / 最高进阶** / 汇总统计 | 地图 seed 与节点状态 / 当前节点 / 层数 / bonus / picks / **本轮遗物 / 金币 / 临时升级 / 封禁列表** / 任务 / **当前事件状态** / board 快照 / runRngState / phase |
| 客户端键 | `STORAGE_KEYS.rogueMeta`（**服务端权威的本地缓存**） | `STORAGE_KEYS.rogueSession` |
| 服务端位置 | `data/match3/<id>.json` 的 `rogue` 段，锁内 `_patchMatch3Store` 合并 | 同文件 `sessions.rogue` 段，不透明保管 + 7 天 TTL |
| 生命周期 | **永久**，只做版本迁移，任何时候不得整段删除 | **单轮**，通关/失败立即墓碑化；过期 TTL 兜底 |
| 权威方 | 服务端扣费/校验，客户端只读缓存 | 客户端产生，服务端只做体积/结构校验与保管 |
| 损坏后策略 | 丢本地缓存，等服务端重新下发 | 放弃续玩、写墓碑、开新轮 |

**事故①：回滚 / 归一时误删永久数据。** 对策三条：

1. 服务端归一化从"白名单重建"改为 **"迁移 → 已知字段就地裁剪 → 未知字段进透传袋 `_ext` 原样回写"**。即老版本服务端读到新版本存档时，不认识的 key 收进 `_ext` 保留并随存档写回，等新版本服务端恢复后数据还在（只有在"宽限期满的显式清理迁移"里才允许删 key）；
2. 沿用既有硬约束：同文件内的星表、meta、sessions 永远经 `_patchMatch3Store` 锁内分段合并，禁止整文件覆盖；
3. 成就徽章属于成就系统（服务端独立存档），**不放进 rogue meta**，避免跨系统混档、互相牵连删除。

**事故②：局内残留带到下一轮。** 对策：

1. `startRun()` 是 run 状态的**唯一构造点**：现有 `bonus / picks / pickedPerks / floor / quest / rewindsLeft / extraPicks` 加上新增的 `map / coins / relics / upgradedPerkIds / bannedPerkIds / eventState` 全部在此集中新建为初始值，不允许从上个闭包或任何存储里继承 run 级字段；
2. `finishRun()` 与新增的 `winRun()` 都必须写墓碑（现有 `finishedSession` 机制保留），墓碑在本地 `loadLocalSession` 与云端 `mergeRemoteSessions` 两条路径上都不会被复活（现有 ts 比较逻辑保留）；
3. **事件状态等瞬态数据只能写 session，禁止写入 rogueMeta**——代码评审与迁移测试各拦一次；
4. 新增单测断言：任意一轮结束后立刻 `startRun()`，上述 run 容器全部等于初始值（用一份"打过事件、买过商店、拿过遗物"的脏 session 做 fixture）。

#### 4.7.4 存档迁移脚本（独立模块，禁止业务代码里散写默认值）

新增字段的默认值**不允许**散落在 `resumeRun` / `normalizeMeta` 的业务分支里（现有的手工 `|| 0` 只保留为迁移之后的最后防线，不再承担结构演进）。默认值与升级步骤集中在独立迁移模块。

**客户端新增 `migrate.js`（纯函数、无 DOM、可被 node 测试直接 import）：**

```js
// 每一步：from → to，只做"增量补默认 + 必要的语义改写"，幂等、无副作用
export const META_MIGRATIONS = [
  {
    from: 1, to: 2,
    up(saved) {
      // 规则一：新增字段——老档没有就深拷贝默认值；绝不动任何已有 key 的值
      saved.unlockedCharacters = saved.unlockedCharacters ?? cloneDefault('unlockedCharacters'); // ['sorcerer']
      saved.relicsFound        = saved.relicsFound        ?? [];
      saved.highestAscension   = saved.highestAscension   ?? 0;
      saved.stats ??= {};
      saved.stats.wins = saved.stats.wins ?? 0;           // 嵌套对象逐键补
      return saved;
    },
  },
  // 规则二：废弃字段——不删，只登记（见 DEPRECATED），读取兼容保留 N 个版本
];

export const SESSION_MIGRATIONS = [
  {
    from: 1, to: 2,
    // 老的"线性冲层"session → 地图版：按 floor 合成一条等价线性地图并标记当前节点；
    // 合成只保结构、不重掷 runRng（沿用现有"续玩不重掷"原则）
    up: (saved) => ({ ...saved, map: synthLinearMap(saved.floor), nodeId: nodeAt(saved.floor), /* coins/relics/... 默认值 */ }),
  },
];

/**
 * 迁移入口
 * @returns {{ver:number, data:object, future:boolean}} future=true 表示存档版本高于当前（回滚）
 */
export function migrateSave(raw, { current, migrations, defaults, kind }) { /* 链式跑 up */ }
```

**服务端**在 `AccountManager` 增加与之同构的 `_migrateRogueMeta(saved)`：置于 `_normalizeRogue` 之前，迁移链与字段白名单以 `config.match3Rogue` 为准；写成**不依赖网络/锁的纯函数**以便单测直接调用。两端迁移规则手工同步（沿用 perks/buffs 双份配置的既有纪律），fixture 共享同一组 JSON。

**迁移规则（评审 checklist）：**

1. **新增字段**：缺 key → 填**深拷贝**的默认值（禁止直接引用共享默认对象，避免多个存档互相串改）；已有 key 一律不覆盖；
2. **废弃字段**：登记进 `DEPRECATED = { 字段: { since, removeAfter, readShim } }`，迁移时**不删除、只标记**；读取处保留 `readShim` 兼容到 `removeAfter` 版本；到期后再发一个专门的清理迁移删除——给版本回滚留出宽窗口；
3. 每个 `up` 必须**幂等**（同档跑两次结果一致）且**纯数据**（不准在迁移里发请求、改配置、碰 DOM）；
4. 迁移只在"加载旧档"时跑一次，完成后立即按新版本写出（本地缓存马上覆盖；服务端在该账号下一次锁内 patch 时落盘）；
5. **session 特例**：session 是临时数据、有 7 天 TTL，迁移性价比低。除"线性→地图"这种必须保续玩的一次外，后续不兼容的大改允许直接放弃旧局（写墓碑、开新轮），不做长期迁移；永久 meta 则必须无限期兼容。

**回滚（新版存档被老版本代码读到）行为：**

- **meta**：不迁移、不报错；逻辑只读当前版本认识的字段，未知字段在服务端进 `_ext` 透传袋保留、在客户端缓存里被忽略也无所谓（服务端是权威，恢复新版后重新下发）；
- **session**：`sessionVer` 高于支持版本时**不续玩**（高版本的局面状态对老代码没有安全读法），不当损坏、不报错，轻提示"该进度来自更新版本"并写本地墓碑防止反复复活；
- 任何读取路径都坚持"取已知字段 + 默认值"，**禁止对未知 key 做存在性强断言而抛错**——这是"不能因为未知 key 直接崩溃"的落地保证。

#### 4.7.5 完整性校验（定位是"损坏检测"，不是防作弊）

先说清边界：本地存档同端可改，任何客户端哈希都**无法防篡改**，也不承诺防篡改（精华/等级/解锁全部服务端权威，改本地拿不到任何收益）。引入轻量校验和的唯一目的是**检测 localStorage 截断、写坏、多版本结构混写**，避免半截对象被迁移成诡异局面。

**版本化字段白名单（本节对需求"新增字段不参与旧档哈希"的直接回答）：**

```js
// 每个版本一份"参与签名的字段集"，随版本冻结、事后不改
const SIGNED_FIELDS = {
  1: ['mode','phase','floor','bonus','picks','baseScore','quest','board','runRngState','ts'],
  2: ['mode','phase','sessionVer','depth','mapSeed','mapState','nodeId','character','ascension',
      'bonus','picks','relics','coins','upgradedPerkIds','bannedPerkIds','quest','board','runRngState','ts'],
};
```

- 写入：对 `SIGNED_FIELDS[该档版本]` 列出的字段做 **canonical JSON**（固定按 key 排序）+ 轻量哈希（FNV-1a 或 djb2，纯 JS 不引依赖），签名存进独立字段 `sig`（session）/ `_ck`（meta 缓存）；**签名字段自身与透传袋 `_ext` 永不参与哈希**；
- 验证：按**存档自己带的版本号**取白名单，而不是按当前代码版本。这样 v2 新增字段天然不在 v1 白名单里——老档永远按 v1 字段集验算，不会因"缺新字段"或"多未知字段"被判损坏；
- **v1 老档没有签名：跳过校验、不判损坏**，在该档下一次被新版本写出时自然带上签名（灰度期零误伤）；
- meta 本地缓存损坏：丢弃缓存并以服务端下发为准（不弹错、不动服务端数据）；
- session 损坏：放弃续玩、写墓碑、开新轮 + 轻提示；
- board 快照虽大但受 32KB 上限约束，默认全量签名；签名计算只发生在"进层/三选一/结算"等已节流的 persist 节点，不跟着每帧连锁跑；
- 校验失败率打点上报，用于发现写入端 bug（而不是用于处罚玩家）。

#### 4.7.6 落点与验收

- 新增：客户端 `migrate.js`（meta/session 双迁移链 + 默认值表 + 签名/验签纯函数）；测试 `tests/match3-save-migration.test.mjs`；
- 修改：`config.js`（`saveVer / SESSION_SCHEMA_VER / SIGNED_FIELDS / DEPRECATED`）、`meta.js`（`normalizeMeta` 改走迁移、保留 `_ext`）、`sync.js`（session 读写过迁移与验签、高版本/损坏档写墓碑）、`mode-rogue.js`（run 状态唯一构造点、winRun 墓碑）；服务端 `config.js`（`match3Rogue.saveVer`）、`AccountManager.js`（`_migrateRogueMeta` + 透传袋 + 版本判定）；
- **fixture 测试矩阵（每个版本一行，固化为仓库内 JSON）**：

| fixture | 断言 |
|---|---|
| v1 真实 meta 快照（取当前线上 `_normalizeRogue` 输出形状） | 迁移后老字段值逐个不变；新字段=默认深拷贝；saveVer 抬到当前 |
| v2 完整 meta | 再跑迁移幂等；签名校验通过 |
| v99（未来版本，带未知 key） | 不抛错；未知 key 进 `_ext` 回写不丢 |
| 含已废弃字段的档 | 字段仍在、readShim 可读、不报错 |
| 缺字段 / 嵌套缺字段的档 | 逐层补齐，老字段不被覆盖 |
| v1 线性 session | 合成线性地图后可续玩、runRng 不重掷 |
| 高版本 / 坏 JSON / 签名不符的 session | 不续玩、不复活、不崩溃、写墓碑 |

## 五、玩家体验优化

1. **节奏分层，消除 30 层重复疲劳**：地图选路（决策停顿）→ 普通层（操作）→ 事件/商店/篝火（喘息与抉择）→ 精英（小高潮）→ 每 10 层 Boss（大高潮）。一张图内主动制造张弛曲线。
2. **区域视觉强提示**：进入新区域换棋盘底色/障碍材质/标题动效（主题系统已有 cyberpunk/forest/ocean，可借鉴），让「我走到哪了」一目了然。
3. **降低选择焦虑**：地图上节点类型图标常显；精英/Boss 预览奖励与风险；三选一卡片沿用现有「下一层实际生效」数值预览，并新增**协同标记**（与已持有遗物联动的祝福高亮）。
4. **新手保护**：前 3 轮 run 的地图减少精英、商店必出且打折、事件少出纯负面；这与现有 `friendlyPicks`（前 2 次保底成长祝福）同一思路，落到 `generateMap(rng,{newPlayer})`。
5. **目标可读性**：多目标层在侧栏用与闯关一致的目标条；Boss 层用血条替代「目标分」，阶段转换有明显演出与文案。
6. **信息可查**：图鉴扩成「祝福 / 遗物 / 角色 / 事件 / Boss」五区；局内可随时查看已持有遗物、地图剩余节点、当前流派协同。
7. **正向反馈**：遗物触发即时飘字/特效（复用 board floats）；连锁返步、清屏等「build 生效瞬间」要有明确反馈，这是肉鸽爽感来源。
8. **结算驱动重开**：通关/死亡页都给「再来一轮」「同角色再冲」「换个角色」三入口；展示进阶解锁进度与「差一点点」的目标，强化再开动机。
9. **单局时长控制**：标定目标普通 run 20–35 分钟（对标杀戮尖塔），靠每层步数与节点数量调控；过长则减少战斗节点数、提高事件/商店密度。
10. **移动端适配**：地图视图与三选一一贯走窄屏折行（现有 perk 模态已处理），节点图需额外做竖向滚动 + 双指缩放的预案。

## 六、开发优先级与里程碑

排序原则：**先搭「结构随机」的骨架（地图+地形+多目标），再补「胜利目标」（Boss），然后填充抉择密度（事件/商店/篝火），再上「build 质变」（遗物），最后给广度与长尾（角色/进阶/硬核）**。每阶段都可独立上线、独立验收、独立标定。

| 阶段 | 内容 | 依赖 | 工作量 | 价值 | 验收标准 |
|---|---|---|---|---|---|
| **P0** | [3.1] 节点地图 + 选路；[3.2] 区域地形(mask/障碍) + 多目标；**[4.7] 存档体系（双版本号 / 两类存档分离 / 迁移脚本 / 版本化校验）** | 无 | **XL** | ⭐⭐⭐⭐⭐ 肉鸽味地基 | 能在随机分叉地图上走到第 30 层；三区域地形切换；层目标含 score/collect/clearBlockers；旧 meta/session 经迁移脚本可续玩、未来版本档与坏档不崩（见 4.7.6 fixture 矩阵全绿）；标定脚本通过 |
| **P1** | [3.3] 精英层 + 数值 Boss（10/20/30）+ 胜利/无尽深渊 + 通关结算与服务端 win | P0 | **L** | ⭐⭐⭐⭐⭐ 给出胜利闭环 | 可「通关」；精英可选路绕开；win 上报与 winBonus 精华正确；新增通关成就 |

| **P5** | [3.8] 角色系统（3 角色 + 解锁 + 角色被动复用遗物） | P3 | **M** | ⭐⭐⭐⭐ 重玩入口身份 | 三角色起手与被动差异可感；按角色统计与解锁条件正确 |
| **P6** | [3.10] 进阶 0–10/15 + [3.9] 死亡墓志铭 + 硬核模式 + 高阶标定 | P1–P5 | **M** | ⭐⭐⭐⭐ 硬核长尾与竞技口径 | 进阶逐级解锁且曲线不断层；硬核独立榜单/成就；死亡页重开转化可埋点 |

建议落地节奏：P0–P1 作为「肉鸽 2.0」第一个可发布大版本（结构随机 + 可通关），P2–P4 作为紧接的内容季，P5–P6 作为留存与硬核版本，P7 长期迭代。

## 八、风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| **范围膨胀** | 一次上全套容易烂尾 | 严格按 P0→P6 切片，P0/P1 先发「结构随机+可通关」大版本；内容（事件/遗物数量）走数据长尾 |

| **引擎改动引入回归** | addBlockers/hook 动到核心消除链路 | P1/P3 先用零引擎档；新增方法与 addSpecials 对称并补引擎单测；hook 默认空数组，不影响其它模式 |
| **金币经济旁路** | 金币若能换精华会变成刷分通道 | 金币局内清零、不兑换精华、不上报发奖；移除服务等都只影响本轮 |
| **新旧存档/续玩兼容 / 回滚炸档** | session 结构大改，在玩的一轮丢失；灰度回滚时老版服务端把新版字段写没；坏 localStorage 被迁移成诡异局面 | **整套机制见 4.7，P0 强制同批落地**：双版本号（meta `saveVer` / session `sessionVer`）+ 独立迁移脚本（新字段补默认不删老字段、废弃字段标记宽限不立即删）；服务端未知字段进 `_ext` 透传袋回写；高版本档不迁移不崩溃（meta 忽略、session 写墓碑不复活）；按档内版本取白名单的版本化签名，新字段不参与旧档哈希、v1 无签名不判损坏；fixture 矩阵覆盖每类档；地图只存 seed+状态而非整图 |
| **两类存档混写** | 事件/遗物等局内状态图省事写进永久 meta，回滚误删或残留到下一局 | 4.7.3 成文分离：run 级数据只进 session，`startRun()` 唯一构造点全新初始化；finish/win 必写墓碑；徽章留在成就系统不进 rogue meta；脏 session 重开断言测试 |
| **服务端双份配置漂移** | 客户端/服务端手工同步已多次强调 | 新增 boss/ascension/角色表两边同改；标定脚本保留服务端常量一致性检查 |
| **硬核/进阶挫败劝退休闲玩家** | 难度分层可能让新手误入 | 进阶默认 0 且明确标注；硬核为独立开关；新手保护地图在前 3 轮生效 |
| **定位拔高带来的美术资源缺口** | Boss/区域/角色需要表现 | 首期全部用 emoji + 现有主题色 + CSS 演出（与现有 codex/特殊元素表现一致），不依赖外部美术资源即可上线 |
