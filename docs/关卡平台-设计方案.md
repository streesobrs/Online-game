## 一、方案概述

### 1.1 这个平台要解决什么

让游戏的内容从「开发完毕即固定」变成「玩家可持续生产」。具体形态：

- 玩家用编辑器制作关卡 / 残局，上传后分享给其他人玩
- 其他玩家浏览、游玩、点赞、收藏、举报
- 官方也能用同一套工具生产关卡

初期服务于消消乐，设计上要能扩展到五子棋残局、围棋残局、象棋残局、推箱子等后续游戏。

### 1.2 核心认知：平台能统一什么，不能统一什么

这是整个设计的前提，判断错了后面全错。

| | 内容 | 说明 |
|---|---|---|
| **能统一** | 关卡的元数据与生命周期 | 创建、编辑、发布、审核、浏览、搜索、点赞、举报、下架、统计 |
| **不能统一** | 关卡的数据结构与语义 | 每种游戏的 payload 结构、编辑器 UI、可解性规则、通关判定 |

因此：**平台对 payload 只存不解析，是黑盒**。所有玩法相关的逻辑都收敛到中间一层「适配器」，由各游戏自己实现。这就是通用性的全部来源。

### 1.3 不做什么

| 不做 | 原因 |
|---|---|
| 平台层的通用编辑器 UI | 各类棋盘差异太大，强行统一会做出一堆特例；编辑器由各游戏自绘，平台只提供外壳容器 |
| 服务端做玩法校验 | 服务端没有游戏引擎，且移植引擎成本远高于收益（见第四章） |
| 跨游戏的关卡互通 | 消消乐的关卡不可能给象棋用，跨游戏只共享"平台能力"，不共享内容 |
| UGC 关卡发放经验与成就 | 会被互刷关卡刷爆（见第七章） |
| 实时联机玩 UGC 残局 | 残局本质是单人解谜，走本地引擎推演即可，不碰联机房间 |

## 二、核心抽象：关卡包与适配器

### 2.1 关卡包（Level Package）

平台存的是「关卡包」，不是「关卡」。关卡包 = 通用外壳 + 游戏私有 payload。

```js
// 集合：levels
{
  levelId: 'lv_7f3a9c',        // 短 id，用于分享链接
  gameType: 'match3',          // 归属游戏
  subType: 'level',            // 同一游戏的关卡形态：level / endgame / puzzle
  schemaVersion: 1,            // payload 的结构版本（该游戏自己的版本号）

  // 通用外壳（平台解析、检索、展示）
  title: '糖果迷宫',
  description: '小心中间的洞，别把红色卡在死角',
  tags: ['中等', '收集'],

  authorId: 'xxx',
  authorName: '昵称',           // 冗余，避免列表页 join
  authorAvatar: 'xxx',

  // 游戏私有数据（平台只存不解析）
  payload: { /* 各游戏自定义结构 */ },
  payloadBytes: 812,
  summary: '8×8 菱形，20 步收集 15 个红色',   // 由 adapter.summarize 生成

  meta: {
    difficulty: 3,             // 作者自评 1~5
    verified: 'auto',          // auto / manual / none，校验程度
  },

  stats: {
    plays: 0, clears: 0, likes: 0, favorites: 0,
    ratingSum: 0, ratingCount: 0, reports: 0,
  },

  status: 'draft',             // draft / pending / published / rejected / removed
  rejectReason: null,
  featured: false,             // 官方精选位

  createdAt: 0, updatedAt: 0, publishedAt: null,
}
```

设计要点：

- **`payload` 是黑盒**：平台代码里不允许出现任何 `payload.xxx` 的字段访问，只能用 adapter 读
- **`summary` 冗余存储**：列表页不启动游戏引擎，由作者保存时用 `adapter.summarize` 生成一次存下来
- **`schemaVersion` 属于游戏**：不是平台版本，用于将来 payload 结构升级时做迁移
- **`subType` 允许一个游戏有多种关卡形态**：消消乐是 `level`，棋类是 `endgame`，推箱子是 `puzzle`

### 2.2 适配器（Adapter）契约

每个接入的游戏实现一个 adapter，平台只通过这组方法与游戏交互。

```js
export const ugcAdapter = {
  gameType: 'match3',
  subType: 'level',
  schemaVersion: 1,
  label: '消消乐',

  // 1. 结构校验：只看结构，不看玩法（与平台服务端的结构校验同构）
  validate(payload) -> { ok: boolean, errors: string[] }

  // 2. 玩法校验：可解性、目标可达性等
  //    level 表示校验强度：strict / loose / none
  //    'none' 是合法返回值 —— 表示这个游戏无法自动校验，平台不得因此拒绝发布
  solveCheck(payload) -> { ok: boolean, level: 'strict' | 'loose' | 'none', reason?: string }

  // 3. 展示文案：列表页用的一句话描述
  summarize(payload) -> string

  // 4. 缩略预览：列表卡片里的静态小图，不启动完整引擎
  renderPreview(payload, hostEl) -> void

  // 5. 编辑器：平台只给容器，UI 由游戏自绘
  mountEditor(hostEl, initialPayload) -> { getPayload(): object, validate(): object }

  // 6. 进入游戏：把外部 payload 喂给引擎
  mountGame(hostEl, payload, callbacks) -> { destroy(): void }
}
```

**契约里最重要的一条**：`solveCheck` 允许返回 `level: 'none'`。因为围棋残局这类关卡本质上无法自动验证（见第五章），平台如果把它当作"校验失败"就会误杀掉大量合法内容。

## 三、数据模型

### 3.1 集合与索引

新增集合 `levels`（沿用现有 `dataStore` 的集合机制）。

| 索引 | 用途 |
|---|---|
| `levelId`（唯一） | 分享链接直达 |
| `gameType + status + publishedAt` | 最新列表 |
| `gameType + status + hotScore` | 热门列表 |
| `authorId + gameType` | 作者主页 |
| `status + createdAt` | 管理端待审队列 |

热门排序用一个简单的分数即可，不必上复杂算法：

```
hotScore = likes * 3 + favorites * 2 + plays * 0.1  → 再按时间衰减
```

### 3.2 服务端硬约束

用户上传的数据会进入存储、列表和客户端渲染，必须在服务端拦住最危险的部分。

| 约束 | 建议值 | 防的是什么 |
|---|---|---|
| `payload` 字节上限 | ≤ 32 KB（消消乐关卡实际只有几 KB） | JSON 炸弹、超大棋盘卡死客户端 |
| JSON 层级深度上限 | ≤ 8 层 | 深层嵌套导致解析卡顿 |
| 字段白名单 | 按 gameType 的静态限制表校验 | 注入意外字段污染存储 |
| 棋盘尺寸上限 | 由各游戏的静态限制表定义（如消消乐 ≤ 12×10） | 超大棋盘 |
| `title` / `description` | ≤ 30 / ≤ 200 字 | 内容滥用 |
| 单账号每日上传数 | ≤ 10 | 刷屏 |
| 单账号草稿数 | ≤ 100 | 存储膨胀 |
| 标签数量 | ≤ 5 个，每个 ≤ 8 字 | 标签灌水 |

**服务端需要一份「各游戏静态限制表」**（不是引擎，只是数值）：

```js
// server/config.js
levelLimits: {
  match3:       { maxBytes: 32768, maxRows: 12, maxCols: 10, schemaVersion: 1 },
  sokoban:      { maxBytes: 32768, maxRows: 20, maxCols: 20, schemaVersion: 1 },
  gobang:       { maxBytes: 16384, maxBoard: 15,      schemaVersion: 1 },
  'chinese-chess': { maxBytes: 16384, schemaVersion: 1 },
  go:           { maxBytes: 16384, maxBoard: 19,      schemaVersion: 1 },
}
```

### 3.3 payload 版本演进

玩法改动会让旧关卡失效，这是 UGC 的固有代价，只能管理、不能消除。

| 措施 | 说明 |
|---|---|
| `schemaVersion` 随 payload 结构变更递增 | 与平台无关，各游戏自己维护 |
| 提供 `migrate(payload, fromVersion)` 迁移函数 | 结构兼容的改动可在加载时自动升级 |
| 不兼容改动：旧关卡标记「已过期」 | 列表仍可见但不可游玩，避免玩家打开后崩溃 |
| 官方关卡与 UGC 关卡分开对待 | 官方关卡随版本更新一起改，UGC 只能靠迁移或标记 |

## 四、校验分层与审核

### 4.1 四层校验，各管一段

| 层 | 执行方 | 能做什么 | 做不到什么 |
|---|---|---|---|
| 结构校验 | **服务端** | JSON 结构、字段白名单、字节与尺寸上限、深度上限 | 任何玩法规则 |
| 玩法校验 | **客户端**（结果随上传提交） | 可解性、目标可达性、初始状态合法性 | 防伪造——结果可被绕过 |
| 人工审核 | 管理员 | 内容合规、明显劣质关卡 | 无法规模化 |
| 玩家举报 | 玩家 | 兜底与事后纠偏 | 时效性差 |

### 4.2 一个必须承认的事实

**服务端没有游戏引擎，所以服务端无法判断"这个关卡能不能通关"。**

- 把引擎移植到服务端成本极高，且要维护两套实现，长期必然不一致
- 客户端跑出来的 `solveCheck` 结果只能作为**参考标记**（`meta.verified`），不能作为保证，因为它可被伪造

因此平台的正确姿势是：**服务端守住"不会造成损害"的底线（体积、结构、频率），玩法质量交给审核 + 举报。** 产品层面不要对外承诺"平台保证所有关卡可通关"。

### 4.3 状态机

```
        创建
         ↓
      draft（草稿，仅作者可见）
         ↓ 提交发布
      pending（待审）
         ↓ 通过        ↘ 驳回
      published        rejected（可修改后重新提交）
         ↓ 被举报/管理员下架
      removed
```

- **发布策略可配置**：`free`（免审直接上架，靠举报兜底）/ `review`（先审后上）。前期建议 `review`，量大了再放开
- 作者可随时把自己的 `published` 改回 `draft` 下架
- `removed` 为管理员强制下架，作者不可自恢复

### 4.4 内容合规的现实情况

**已核实：项目当前没有任何文本内容过滤能力。** 服务端只有"不返回敏感字段"这类注释，聊天也不存在敏感词过滤。

所以开放上传前必须先解决其中一项：

| 方案 | 成本 | 适用 |
|---|---|---|
| 加一套敏感词过滤（标题 / 描述 / 标签） | 低 | 必做，无论是否人工审核 |
| 人工审核队列（复用现有管理端体系） | 中 | 前期量小可行 |
| 邀请制 / 白名单上传 | 极低 | 先只对部分玩家开放，验证后再放开 |

建议顺序：**先加敏感词过滤 + 邀请制 → 量起来后再上人工审核队列 → 最后考虑免审。**

## 五、各游戏能力矩阵

这是判断"平台能不能真的普及到多个游戏"的关键依据。结论：**能接入，但各游戏的校验能力和改造成本差异极大**。

| 游戏 | 关卡形态 | 能自动校验什么 | 校验强度 | 接入成本 | 特别风险 |
|---|---|---|---|---|---|
| 消消乐 | `level` | 初始无三连、至少一个可行步；目标可达性可放宽 | 强 | 低（引擎已是纯逻辑） | 低 |
| 推箱子 | `puzzle` | 关卡是否可解（搜索 + 时限） | 中（时限内） | 中（游戏本体尚不存在） | 状态空间爆炸 |
| 五子棋 | `endgame` | 先手必胜 / 必和的判定 | 中~强 | 中~高 | 残局是单人玩法，与联机流程冲突 |
| 象棋 | `endgame` | "N 步杀" | 中~强 | 中~高 | 长将、重复局面判定 |
| 围棋 | `endgame` | 死活题可解性 | 弱 | 高 | 劫争、让子、非空局面初始化；"优势局面"完全不可验证 |

可直接读出的结论：

- **消消乐是最合适的首个接入游戏**：校验强、成本低、引擎天然是纯逻辑
- **围棋是难度天花板**：需要先确认它的引擎是否支持从非空局面启动，且要接受"部分残局无法自动校验"
- **推箱子的可解性验证是 PSPACE-complete**：只能用搜索 + 时限，超时就返回 `level: 'none'`，不能当作失败

## 六、游戏接入改造成本

每个游戏接入平台，都要改这些地方（**这部分成本常被低估**）：

| # | 改造项 | 说明 |
|---|---|---|
| 1 | 引擎支持从外部局面启动 | 不能假设空棋盘；所有内部状态都要能由 payload 完全确定 |
| 2 | 对局流程支持非标准起始状态 | 着法历史、悔棋、重复局面判定、胜负判定初始化都要重新走查 |
| 3 | 结算回调 | 通关 / 失败上报平台（但不发经验，见第七章） |
| 4 | 实现 adapter | 六个方法 |
| 5 | 退出路径 | 游玩 UGC 关卡时能返回平台列表 |

### 6.1 棋类残局的特殊问题

五子棋、围棋、象棋都是**联机对战游戏**，而残局是**单人玩法**。不要试图复用联机房间流程。

建议：**残局模式完全复用「单人本地对局」路径**——本地引擎推演 + 本地胜负判定，完全不碰 socket 对战、匹配、房间。这样可以避开协议层的全部兼容问题。

需要重点走查的两处规则陷阱：

- **围棋的劫争**：从非空局面开始时，劫争状态（打劫禁着点）无法从静态局面推出来，必须明确定义"残局初始无劫"或让 payload 携带劫的上下文
- **象棋的重复局面 / 长将**：判定依赖历史，残局起始时需要定义一个"历史为空"的基准

## 七、红线：UGC 不发放经验与成就

### 7.1 为什么必须定死

如果 UGC 关卡能发经验、计成就、进排行榜：两个玩家互相制作一个「一步通关」的关卡，对着刷就能刷爆等级榜和成就。任何客户端校验都拦不住，因为上传的是合法关卡。

### 7.2 具体规则

| 内容来源 | 经验 | 成就 | 排行榜 | 可统计 |
|---|---|---|---|---|
| 官方关卡（内置） | ✅ 发放 | ✅ 计入 | ✅ 计入 | 正常 |
| UGC 关卡 | ❌ 不发 | ❌ 不计 | ❌ 不进 | 通关数 / 获赞数等弱指标 |

**关键区分**：不是"消消乐不发经验"，而是"**UGC 关卡不发经验**"。消消乐的 30 关官方关卡照常发经验、计成就、进排行榜。

### 7.3 由此推出的架构结论

UGC 必须是**独立子系统**，不能并入现有对战/战绩体系：

- 不调用 `updateGameStats`
- 不与 `games` / `stats` 的既有字段混用
- 游玩记录单独存，只在"我的作品"「玩过的关卡」这类独立页面上体现
- 上传数量、获赞数可以做成独立的轻量成就（如"作品获赞 100"），这类指标无法通过刷关卡获得

这与 `消消乐-开发方案.md` 第十章对 match3 的硬约束方向完全一致。

## 八、接口设计

### 8.1 REST（列表与内容）

列表类走 REST，便于缓存和分享链接。

```
GET    /api/levels?gameType=match3&sort=hot&page=1&pageSize=20&q=关键词&tag=中等
GET    /api/levels/:levelId
GET    /api/levels/:levelId/raw                  # 分享直达，返回 payload + 元信息
GET    /api/users/:accountId/levels?gameType=match3&page=1

POST   /api/levels                               # 创建草稿
PUT    /api/levels/:levelId                      # 更新（仅作者）
POST   /api/levels/:levelId/publish              # 提交发布
DELETE /api/levels/:levelId                      # 删除（仅作者，草稿或已下架）

POST   /api/levels/:levelId/like                 # 点赞 / 取消点赞
POST   /api/levels/:levelId/favorite             # 收藏 / 取消
POST   /api/levels/:levelId/report               # 举报
POST   /api/levels/:levelId/play                 # 游玩计数（可批量）
```

管理端复用现有管理端体系：待审列表、通过 / 驳回、下架、封禁作者。

### 8.2 分享链接

建议用**与游戏无关的平台路由**，由平台层解析 `gameType` 后跳转到对应游戏：

```
/beta/#/level/:levelId
```

平台层拿到 `levelId` → 读 `gameType` → 跳到对应游戏的视图并把 payload 传进去。这样任何游戏的分享链接形态都一致，将来加游戏不用改链接规则。

### 8.3 关于 Socket

不建议把点赞、计数这类高频小操作走 socket。用 REST 批量上报即可，避免给现有的 socket 层增加无关的实时协议。

## 九、编辑器设计

### 9.1 分层

| 层 | 负责 |
|---|---|
| 平台层（外壳） | 标题、描述、标签、难度自评、保存草稿、校验结果提示、提交发布、预览区 |
| 游戏层（自绘） | 编辑区本体：`mountEditor(hostEl, initialPayload)` |

平台只提供容器和提交按钮，编辑区内部完全由游戏自己实现——这是唯一可行的方案，因为各类棋盘的操作方式差异太大。

### 9.2 编辑器的第一用途不是 UGC

**建议编辑器先内部使用，用来生产官方关卡，再对外开放。**

理由：

- 消消乐要配 30 关，手写 JSON 很容易出错（mask、障碍坐标、目标数值），编辑器能显著提速并减少错误
- 编辑器在第一阶段就有明确价值，不是"为未来做的无用功"
- 内部用一段时间后，与平台对接的接口会被打磨得比较稳定，再开放给玩家风险更低

因此编辑器的排序应当是：**内部工具 → 开放上传 → 社区化**，而不是一步到位做创意工坊。

---

## 十、分阶段路线与验收标准

| 阶段 | 内容 | 前置依赖 |
|---|---|---|
| **0** | 消消乐首版满足 UGC-ready 约束（payload 纯数据、可序列化、可校验、可从外部加载） | 无，随消消乐首版一起做，成本几乎为零 |
| **1** | 消消乐关卡编辑器（**内部用**，生产官方 30 关） | 消消乐玩法稳定 |
| **2** | 平台最小闭环：`levels` 存储 + 浏览 + 游玩 + 分享链接 + 举报 | 编辑器可用 |
| **3** | 社区体验：点赞收藏、作者主页、搜索排序、难度标签、热门/最新 | 阶段 2 |
| **4** | 内容合规：敏感词过滤 + 邀请制 / 人工审核队列 | 开放上传前必须完成 |
| **5** | **接入第二个游戏**（建议推箱子或象棋残局） | 阶段 3 稳定 |
| **6** | 铺开其余游戏 | 阶段 5 通过 |

### 唯一的验收标准

> **接入第二个游戏时，平台层零改动，只新增该游戏的 adapter。**

这是判断抽象是否成立的硬指标：

- 如果接第二个游戏时平台层要大改 → 说明抽象错了，**此时改还来得及**
- 如果一直没验证，接了五个游戏后才发现抽象错了 → 返工成本极高

阶段 5 存在的唯一目的就是做这个验证，不能跳过。

## 十一、风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| 抽象过早，接口设计过度通用或不够通用 | 后期重构 | 用「第二个游戏零改动」作为验收标准；阶段 0 只做约束不做框架 |
| 玩法改动导致已上传关卡失效 | 内容作废、玩家流失 | `schemaVersion` + 迁移函数 + 不兼容时标记「已过期」而非崩 |
| 畸形 payload 打崩引擎 | 客户端白屏 / 服务端卡顿 | 服务端硬约束 + `adapter.validate` + 引擎入口 try/catch 三层防护 |
| 内容合规缺位（项目当前无文本过滤） | 违规内容上架 | 开放上传前必须先加敏感词过滤 + 邀请制 |
| UGC 被用于刷经验 | 等级 / 成就体系失真 | 第七章红线：UGC 不发经验、不计成就、不进排行榜 |
| 服务端无法校验可解性 | 出现不可通关的关卡 | 产品层不承诺"保证可解"；靠作者自测 + 举报 + 差评下架 |
| 存储与草稿膨胀 | 数据库增长 | 上传频率与草稿数上限，定期清理长期未发布的草稿 |
| 编辑器先对外开放，接口不稳 | 体验差、返工 | 编辑器先内部用（第九.2），稳定后再开放 |

## 十二、未来展望

储备方向，不在当前路线内：

- **单关挑战榜**：同一关的最快通关 / 最高分排名（注意：这不属于 UGC 发经验的场景，是关卡内的独立榜单，不冲突）
- **关卡合集 / 章节包**：作者把若干关卡打包成一个系列
- **限时挑战赛**：官方指定一个 UGC 关卡做限时活动
- **官方精选位**：`featured` 已预留
- **关卡评分体系**：现有 `ratingSum / ratingCount` 已预留，可用差评率自动下架劣质关卡
- **跨游戏成就**：「作品被游玩 1000 次」这类创作者向成就，无法通过刷关卡获得
